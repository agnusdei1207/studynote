## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 컨슈머 그룹 (Consumer Group)은 아파치 카프카 (Apache Kafka)에서 같은 `group.id`를 공유하는 여러 컨슈머가 토픽 파티션을 나눠 읽도록 만드는 병렬 처리 단위다.
> 2. **가치**: 그룹 내부에서는 각 파티션이 한 컨슈머에만 할당되므로 중복 소비를 막으면서 처리량을 수평 확장할 수 있고, 장애 시 리밸런싱으로 가용성도 확보된다.
> 3. **판단 포인트**: 처리량 상한은 컨슈머 수가 아니라 파티션 수와 키 분포가 결정하므로, 파티션 설계·오프셋 커밋·순서 보장 범위를 함께 계획해야 한다.

---

## Ⅰ. 개요 및 필요성

컨슈머 그룹은 많은 이벤트를 한 대의 소비자가 모두 처리하기 어려울 때, 동일한 역할의 여러 인스턴스를 하나의 논리 팀으로 묶어 병렬 소비하게 만드는 구조다. 카프카는 브로커가 매우 빠르기 때문에 생산 속도는 높은데, 실제 비즈니스 로직을 수행하는 소비자 애플리케이션이 더 느린 경우가 많다. 이때 단일 컨슈머만 두면 컨슈머 랙 (Consumer Lag)이 누적되고, 실시간 처리 목표를 만족하기 어렵다.

그렇다고 동일한 메시지를 여러 인스턴스가 제각각 읽게 두면, 같은 주문을 여러 번 처리하거나 같은 알림을 중복 발송하는 문제가 생긴다. 컨슈머 그룹은 바로 이 지점을 해결한다. 같은 그룹 안에서는 메시지를 공평하게 나눠 처리하고, 다른 그룹은 같은 메시지를 독립적으로 다시 읽을 수 있게 해 처리 공유와 기능 분리를 동시에 만족시킨다.

- **📢 섹션 요약 비유**: 한 사람에게 몰린 택배를 같은 팀 기사들이 구역별로 나눠 배달하게 하되, 같은 상자를 두 사람이 동시에 배달하지 않게 만드는 것과 같다.

## Ⅱ. 아키텍처 및 핵심 원리

카프카 토픽은 여러 파티션 (Partition)으로 나뉘며, 컨슈머 그룹 코디네이터 (Group Coordinator)는 그룹에 속한 컨슈머에게 이 파티션들을 배정한다. 같은 그룹 안에서는 한 파티션이 한 시점에 하나의 컨슈머에게만 할당된다. 컨슈머는 자신이 읽은 위치를 오프셋 (Offset)으로 관리하고, 커밋된 오프셋을 기준으로 재시작이나 장애 복구 후 이어서 처리한다.

아래 그림은 기본적인 파티션 할당 구조를 보여 준다.

```text
+----------------------------------------------------------------------+
| Kafka consumer group assignment                                      |
+----------------------------------------------------------------------+
| Topic: orders                                                        |
|   P0 -----------------------------> Consumer A                       |
|   P1 -----------------------------> Consumer B                       |
|   P2 -----------------------------> Consumer C                       |
|                                                                      |
| If Consumer B fails -> rebalance -> P1 moves to A or C              |
+----------------------------------------------------------------------+
```

| 요소 | 역할 | 설계 포인트 |
| :--- | :--- | :--- |
| 파티션 | 병렬 처리 단위 | 수가 곧 최대 병렬성의 상한이 된다 |
| 컨슈머 그룹 | 동일 업무 인스턴스 묶음 | 같은 그룹은 분산 처리, 다른 그룹은 독립 소비 |
| 오프셋 | 읽은 위치 기록 | 커밋 시점이 중복 처리와 유실 위험을 좌우 |
| 리밸런싱 (Rebalancing) | 장애·증설 시 파티션 재할당 | 잦으면 처리 지연과 일시 중지가 커진다 |
| 키 분배 | 같은 키를 같은 파티션으로 보냄 | 주문 단위 순서 보장과 부하 균형을 함께 고려 |

핵심은 병렬성과 순서 보장 범위가 파티션 단위라는 점이다. 같은 키를 같은 파티션으로 보내면 해당 키의 순서는 지킬 수 있지만, 토픽 전체의 절대 순서는 보장되지 않는다. 또한 컨슈머를 많이 늘려도 파티션 수가 부족하거나 특정 파티션에 트래픽이 몰리면 실제 처리량은 기대만큼 늘지 않는다.

- **📢 섹션 요약 비유**: 여러 계산원이 있어도 계산대가 세 개뿐이면 동시에 처리할 수 있는 손님 줄도 세 줄뿐인 것과 같다.

## Ⅲ. 비교 및 연결

컨슈머 그룹을 이해하려면 "같은 그룹"과 "다른 그룹"의 차이를 분명히 알아야 한다. 같은 그룹의 컨슈머들은 일을 나눠 갖는 협업 관계이고, 다른 그룹들은 같은 메시지를 각자 전체 복사본처럼 읽는 독립 관계다. 예를 들어 주문 토픽을 결제 그룹과 분석 그룹이 각각 구독하면, 두 그룹은 같은 메시지를 모두 읽지만 그룹 내부에서는 파티션을 분산 처리한다.

| 구조 | 메시지 소비 방식 | 적합한 상황 | 주의점 |
| :--- | :--- | :--- | :--- |
| 같은 그룹 | 파티션을 분할해 한 번씩 처리 | 같은 업무의 수평 확장 | 파티션 수보다 많이 늘려도 효과 제한 |
| 다른 그룹 | 각 그룹이 전체 메시지를 독립 소비 | 결제, 알림, 분석 등 기능 분리 | 그룹별 랙과 실패를 따로 관리해야 함 |
| 단일 컨슈머 | 한 인스턴스가 전부 처리 | 트래픽이 작고 순서가 단순한 경우 | 병목과 장애 단일점이 되기 쉬움 |

또한 컨슈머 그룹은 이벤트 기반 아키텍처와 자연스럽게 연결된다. 브로커가 이벤트를 저장하고, 컨슈머 그룹이 이를 병렬 소비해 서비스별 후속 처리를 수행한다. 이때 멱등성, 데드 레터 큐, 정확히 한 번 의미론 (Exactly-Once Semantics) 같은 개념이 함께 등장하며, 특히 오프셋 커밋 시점과 외부 부수 효과의 순서를 어떻게 맞출지가 실무 핵심이 된다.

- **📢 섹션 요약 비유**: 한 방송을 여러 팀이 각자 듣는 것은 가능하지만, 같은 팀 안에서는 대본 페이지를 서로 나눠 읽어야 중복 발표를 막을 수 있는 것과 같다.

## Ⅳ. 실무 적용 및 실무자 판단

실무에서는 먼저 목표 처리량과 키 기반 순서 요구를 보고 파티션 수를 정해야 한다. 파티션 수는 나중에 늘릴 수 있지만, 키 해시 분포와 소비 순서에 영향을 주므로 초기 설계가 중요하다. 또한 자동 커밋을 무심코 켜 두면 데이터베이스 반영 전에 오프셋이 먼저 기록되어 장애 시 메시지가 유실된 것처럼 보일 수 있으므로, 커밋 시점과 부수 효과 완료 순서를 명확히 정의해야 한다.

### 실무자 판단 체크리스트

1. 목표 처리량을 기준으로 파티션 수와 컨슈머 수의 상한을 계산했는가?
2. 같은 주문, 회원, 계좌처럼 순서가 중요한 키는 같은 파티션으로 보내고 있는가?
3. 오프셋 커밋이 외부 저장소 반영 후에 이뤄지도록 설계했는가?
4. 리밸런싱 빈도를 줄이기 위해 정적 멤버십, 협력적 재조정 등 운영 옵션을 검토했는가?
5. 컨슈머 랙, 처리 시간, 재시도 횟수, 독성 메시지를 모니터링하고 있는가?

### 자주 나오는 안티패턴

- 컨슈머 인스턴스만 늘리고 파티션 수는 그대로 둔 채 성능 향상을 기대하는 구조
- 글로벌 순서를 보장하지 않는데도 전체 토픽 순서를 가정한 비즈니스 로직
- 자동 커밋에만 의존해 외부 시스템 반영 실패 시 중복 또는 누락 분석이 어려운 구조
- 키 분배가 치우쳐 특정 파티션만 과열되는 구조

학습 정리에서는 컨슈머 그룹을 단순한 부하 분산 기능으로만 쓰지 말고, 파티션 설계와 오프셋 전략이 함께 있어야 완전한 처리 모델이 된다고 정리하는 것이 좋다. 병렬성, 순서, 복구를 하나의 세트로 보는 관점이 중요하다.

- **📢 섹션 요약 비유**: 팀원을 늘리는 것만으로 일이 빨라지는 것이 아니라, 작업 칸을 충분히 나누고 누가 어디까지 했는지 체크표를 남겨야 진짜 분업이 되는 것과 같다.

## Ⅴ. 기대효과 및 결론

컨슈머 그룹은 카프카 기반 시스템에서 처리량 확장과 장애 복구를 동시에 가능하게 하는 핵심 메커니즘이다. 같은 업무를 수행하는 인스턴스를 수평 확장하면서도 그룹 내부 중복 처리를 피할 수 있고, 장애가 나도 남은 인스턴스로 파티션을 재배치해 서비스를 이어 갈 수 있다. 따라서 대규모 이벤트 파이프라인에서 컨슈머 그룹은 운영 탄력성의 중심이 된다.

그러나 파티션 수, 키 분포, 리밸런싱 비용, 오프셋 전략을 잘못 잡으면 기대한 효과가 나오지 않는다. 결국 기억해야 할 핵심은 "컨슈머를 늘리면 빨라진다"가 아니라, <strong>파티션이 병렬성의 단위이고 컨슈머 그룹은 그 단위를 안전하게 배분하는 구조</strong>라는 점이다. 이 관점을 잡아야 카프카 튜닝과 장애 분석이 선명해진다.

- **📢 섹션 요약 비유**: 여러 명이 책을 읽어 주더라도 책이 장별로 잘 나뉘어 있고 어디까지 읽었는지 책갈피가 있어야 끊김 없이 이어 읽을 수 있는 것과 같다.

### 📌 관련 개념 맵

| 개념 | 연결 포인트 |
| :--- | :--- |
| 파티션 (Partition) | 카프카 병렬 처리와 순서 보장의 기본 단위다. |
| 오프셋 (Offset) | 컨슈머가 어디까지 읽었는지 나타내는 위치 정보다. |
| 컨슈머 랙 (Consumer Lag) | 생산 속도와 소비 속도 차이를 측정하는 핵심 운영 지표다. |
| 리밸런싱 (Rebalancing) | 장애나 증설 시 파티션 소유권을 다시 배분하는 절차다. |
| 멱등성 (Idempotency) | 재시도나 중복 소비 상황에서도 결과를 안정적으로 유지한다. |
| Exactly-Once Semantics | 오프셋과 처리 결과의 일관성을 강화하려는 고급 처리 보장 모델이다. |

### 📈 관련 키워드 및 발전 흐름도

```text
단일 컨슈머 병목과 Lag 증가
        |
        v
토픽 파티션 분할
        |
        v
Consumer Group 기반 병렬 소비
        |
        v
Offset 관리 · Rebalancing · Lag 모니터링
        |
        v
멱등성 · Exactly-Once Semantics 최적화
```

이 흐름은 단순 메시지 소비에서 시작해, 점차 병렬 처리와 복구 전략이 정교해지는 카프카 운영 성숙도를 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. 큰 상자들을 한 사람이 다 옮기면 너무 오래 걸려요.
2. 그래서 친구들이 팀을 만들어 상자를 구역별로 나눠 옮겨요.
3. 누가 어디까지 했는지 표시해 두면, 친구 한 명이 쉬어도 다른 친구가 이어서 할 수 있어요.
