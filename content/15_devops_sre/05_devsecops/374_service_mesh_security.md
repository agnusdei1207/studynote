## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 서비스 메시 보안은 마이크로서비스 간 모든 통신을 **사이드카 프록시(Envoy)**를 통해 자동으로 mTLS 암호화하고, 서비스 ID 기반 인증·인가·관측을 애플리케이션 코드 변경 없이 인프라 계층에서 일괄 적용하는 보안 패턴이다.
> 2. **가치**: 개발자가 TLS 인증서 관리, 재시도, 트래픽 정책을 직접 구현할 필요 없이, Istio/Linkerd가 SPIFFE 서비스 ID와 AuthorizationPolicy로 제로 트러스트 마이크로세그멘테이션을 자동 실현한다.
> 3. **판단 포인트**: 서비스 메시는 L7 가시성과 정책 세분화라는 강력한 이점이 있지만, 사이드카 리소스 오버헤드(CPU 10-15%, 메모리 50-100MB/Pod)와 운영 복잡성을 고려해 도입 범위와 시점을 판단해야 한다.

---

## Ⅰ. 개요 및 필요성

모놀리스에서 마이크로서비스로 전환하면 서비스 간 네트워크 호출이 폭증한다. 전통적 경계 기반 보안(방화벽, 네트워크 ACL)은 서비스 단위의 세밀한 접근 제어를 제공하지 못한다. 내부 통신이 평문(HTTP)으로 전송되면, 컨테이너 탈출이나 네트워크 스니핑으로 민감 데이터가 노출된다.

서비스 메시는 각 Pod에 사이드카 프록시를 주입하여 모든 인바운드/아웃바운드 트래픽을 가로채고, 자동 mTLS(상호 TLS)로 암호화한다. 이는 Zero Trust의 "모든 통신을 암호화하라"는 원칙을 인프라 수준에서 강제한다.

- 📢 섹션 요약 비유: 회사 내부 전화를 모두 도청 방지 전화기로 교체하되, 직원들은 사용법을 바꿀 필요가 없는 것이다.

## Ⅱ. 아키텍처 및 핵심 원리

```text
+---------------------------------------------------------+
|              서비스 메시 보안 아키텍처                     |
+---------------------------------------------------------+
|  [Control Plane: Istiod]                                 |
|  - CA (인증서 자동 발급/로테이션)                          |
|  - Policy Engine (AuthorizationPolicy)                   |
|  - xDS API (설정 배포)                                    |
|       |                                                   |
|  +----v--------+    mTLS    +----------------+           |
|  | Pod A       | <----------> | Pod B          |           |
|  | +---------+ |            | +-------------+|           |
|  | |App      | |            | |App          ||           |
|  | +----+----+ |            | +------+------+|           |
|  | +----v----+ |            | +------v------+|           |
|  | |Envoy    | |            | |Envoy        ||           |
|  | |Sidecar  | |            | |Sidecar      ||           |
|  | +---------+ |            | +-------------+|           |
|  +-------------+            +----------------+           |
+---------------------------------------------------------+
```

| 구성 요소 | 역할 | 보안 기능 |
| :--- | :--- | :--- |
| Istiod | 컨트롤 플레인 통합 | CA, 정책 배포, xDS |
| Envoy Sidecar | 데이터 플레인 프록시 | mTLS 종단, L7 관측, 레이트 리밋 |
| PeerAuthentication | mTLS 모드 설정 | STRICT/PERMISSIVE/DISABLE |
| AuthorizationPolicy | L7 접근 제어 | 서비스/경로/메서드 기반 ALLOW/DENY |
| RequestAuthentication | JWT 검증 | OIDC 토큰 유효성 확인 |

- 📢 섹션 요약 비유: Istiod는 보안 관제 센터(Control Tower), Envoy는 각 사무실 문 앞의 경비원, mTLS는 경비원끼리 서로 신분증을 확인하는 절차다.

## Ⅲ. 비교 및 연결

| 비교 항목 | 전통 네트워크 보안 | 서비스 메시 보안 | API Gateway 보안 |
| :--- | :--- | :--- | :--- |
| 적용 위치 | 네트워크 경계 | 서비스 간(East-West) | 진입점(North-South) |
| 암호화 단위 | 네트워크 세그먼트 | Pod-to-Pod mTLS | 클라이언트-게이트웨이 TLS |
| 정책 세분화 | IP/Port 기반 | 서비스 ID/HTTP 경로 기반 | API 엔드포인트 기반 |
| 관측 가능성 | L3/L4 로그 | L7 메트릭/트레이스 | API 호출 로그 |
| 인증서 관리 | 수동/외부 CA | 자동 발급/로테이션 | 수동 관리 |

- 📢 섹션 요약 비유: 네트워크 보안은 건물 입구 경비, 서비스 메시는 각 방문 앞 경비, API Gateway는 방문객 리셉션 데스크다.

## Ⅳ. 실무 적용 및 실무자 판단

**체크리스트 (5가지)**
- [ ] PeerAuthentication을 STRICT 모드로 설정해 mTLS를 강제
- [ ] AuthorizationPolicy로 최소 권한 원칙 기반 서비스 간 접근 제어 정의
- [ ] Istio CA 인증서 루트를 조직 PKI와 연동하고 로테이션 주기 확인
- [ ] 사이드카 리소스 제한(CPU/Memory limit)을 설정하고 오버헤드 모니터링
- [ ] Ambient Mesh(사이드카리스) 모드 적용 가능성 평가로 리소스 최적화

**안티패턴**
- ❌ PERMISSIVE 모드를 프로덕션에서 방치 -> 평문 통신 허용으로 보안 무효화
- ❌ AuthorizationPolicy 없이 mTLS만 적용 -> 인증만 있고 인가가 없는 상태
- ❌ 사이드카 리소스 무제한 할당 -> 노드 자원 고갈 및 OOM
- ❌ 서비스 메시 업그레이드 시 데이터 플레인/컨트롤 플레인 버전 불일치

- 📢 섹션 요약 비유: 경비원(사이드카)을 배치했지만 출입 규칙(정책)을 안 정하면 아무나 통과시키는 형식적 경비가 된다.

## Ⅴ. 기대효과 및 결론

서비스 메시 보안은 마이크로서비스 아키텍처에서 Zero Trust를 코드 변경 없이 인프라 계층에서 실현하는 가장 실용적인 방법이다. mTLS 자동화, 서비스 ID 기반 정책, L7 관측을 통해 보안·운영·개발을 분리하면서도 통합한다. Ambient Mesh, eBPF 기반 메시 등 차세대 기술이 사이드카 오버헤드를 줄이며, 서비스 메시는 클라우드 네이티브 보안의 표준 인프라로 자리잡고 있다.

- 📢 섹션 요약 비유: 회사 전체에 도청 방지·신분 확인·출입 기록이 자동으로 작동하는 보안 시스템을 깔아, 직원들은 업무에만 집중할 수 있다.

### 📌 관련 개념 맵

| 개념 | 연결 관계 | 참조 영역 |
| :--- | :--- | :--- |
| mTLS | 서비스 간 상호 인증 | 네트워크 보안 |
| Zero Trust | 서비스 메시로 인프라 적용 | 보안 아키텍처 |
| SPIFFE/SPIRE | 서비스 ID 표준 | 클라우드 네이티브 |
| Envoy Proxy | 데이터 플레인 구현체 | 인프라 |
| Network Policy | K8s L3/L4 보완 관계 | 컨테이너 보안 |

### 📈 관련 키워드 및 발전 흐름도

```text
IP 기반 방화벽 ACL
  -> Kubernetes Network Policy (L3/L4)
    -> Service Mesh Sidecar (L7 mTLS)
      -> Ambient Mesh (Sidecar-less)
        -> eBPF 기반 Service Mesh (Cilium)
          -> 통합 Zero Trust 네트워크 플랫폼
```

### 👶 어린이를 위한 3줄 비유 설명

1. 서비스 메시 보안은 학교에서 친구에게 쪽지를 보낼 때, 보이지 않는 보호막이 자동으로 쪽지를 감싸서 다른 사람이 못 읽게 하는 거예요.
2. mTLS는 두 친구가 서로 학생증을 보여주고 확인한 다음에만 대화하는 규칙이에요.
3. 사이드카는 매 교실 문 앞에 서 있는 친절한 경비 로봇으로, 누가 들어오는지 자동으로 확인해줘요.
