## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 소프트웨어 공급망 보안(Software Supply Chain Security)은 코드 작성부터 빌드·배포·실행까지 모든 의존성과 아티팩트의 출처·무결성·취약점을 추적·검증하여, 공급망 공격(Supply Chain Attack)을 원천 차단하는 엔드-투-엔드 보안 체계다.
> 2. **가치**: SBOM(Software Bill of Materials)은 소프트웨어의 "성분표"로, CycloneDX·SPDX 표준으로 모든 의존성을 명시적으로 관리하고 CVE 매핑을 자동화하여 SolarWinds·Log4Shell급 공격의 영향 범위를 즉시 식별할 수 있게 한다.
> 3. **판단 포인트**: 미국 행정명령(EO 14028), EU Cyber Resilience Act 등 SBOM 제출이 법적 요구사항이 되면서, SBOM 생성·검증·배포 파이프라인은 규제 준수의 필수 요소가 되었다.

---

## Ⅰ. 개요 및 필요성

현대 소프트웨어의 80-90%는 오픈소스 라이브러리로 구성된다. 직접 작성한 코드보다 서드파티 의존성이 훨씬 많으므로, 의존성 하나의 취약점이 전체 시스템을 위험에 빠뜨린다. 2020년 SolarWinds(빌드 시스템 침투), 2021년 Log4Shell(오픈소스 취약점), 2022년 npm 패키지 탈취 등 공급망 공격이 급증하고 있다.

SBOM은 소프트웨어에 포함된 모든 컴포넌트, 버전, 라이선스, 취약점을 투명하게 문서화한다. 이를 CI/CD 파이프라인에 통합하면 빌드 시점에 자동으로 SBOM을 생성하고, 배포 전 취약점을 검증할 수 있다.

- 📢 섹션 요약 비유: 식품의 성분표처럼, 소프트웨어에도 "이 프로그램은 어떤 재료로 만들었는지"를 적어두는 것이다. 알레르기(취약점) 유발 성분이 있는지 바로 확인할 수 있다.

## Ⅱ. 아키텍처 및 핵심 원리

```text
+---------------------------------------------------------+
|         소프트웨어 공급망 보안 파이프라인                   |
+---------------------------------------------------------+
|  [소스 코드] -> [의존성 해석] -> [빌드]                     |
|       |              |             |                      |
|  서명 검증       SCA 스캔      SBOM 생성                  |
|  (Sigstore)    (Snyk/Grype)  (Syft/CycloneDX)           |
|       |              |             |                      |
|  [아티팩트 저장소] <- 서명(Cosign) + SBOM 첨부             |
|       |                                                   |
|  [배포 게이트] -> 정책 검증(OPA) + 취약점 차단              |
|       |                                                   |
|  [프로덕션 런타임] -> 지속적 SBOM 모니터링                  |
+---------------------------------------------------------+
```

| SBOM 표준 | 주관 | 형식 | 특징 |
| :--- | :--- | :--- | :--- |
| CycloneDX | OWASP | JSON/XML/Protobuf | 보안 중심, VEX 지원 |
| SPDX | Linux Foundation | JSON/RDF/Tag-Value | 라이선스 중심, ISO 표준 |
| SWID | ISO/NIST | XML | 소프트웨어 식별 태그 |

| 공급망 보안 프레임워크 | 핵심 개념 |
| :--- | :--- |
| SLSA (Supply-chain Levels for Software Artifacts) | 빌드 출처 증명 레벨(L1-L4) |
| in-toto | 빌드 파이프라인 레이아웃 검증 |
| Sigstore (Cosign/Fulcio/Rekor) | 키리스 서명·투명성 로그 |

- 📢 섹션 요약 비유: SLSA는 식품의 HACCP 인증 등급, SBOM은 성분표, Sigstore는 위변조 방지 봉인 스티커다.

## Ⅲ. 비교 및 연결

| 비교 항목 | SCA(의존성 스캔) | SBOM(성분표 관리) | SLSA(출처 증명) |
| :--- | :--- | :--- | :--- |
| 목적 | 취약점 탐지 | 구성 투명성 | 빌드 무결성 |
| 시점 | 개발/빌드 | 빌드/배포 | 빌드 |
| 산출물 | 취약점 리포트 | BOM 문서 | 출처 증명서(Provenance) |
| 도구 예시 | Snyk, Grype | Syft, Trivy | SLSA GitHub Generator |
| 법적 요구 | 권고 | EO 14028 의무화 | NIST 권고 |

- 📢 섹션 요약 비유: SCA는 식품 안전 검사관, SBOM은 성분표 라벨, SLSA는 "이 공장에서 이 절차로 만들었다"는 생산 이력 증명서다.

## Ⅳ. 실무 적용 및 실무자 판단

**체크리스트 (5가지)**
- [ ] CI 파이프라인에 Syft/Trivy로 SBOM 자동 생성 및 CycloneDX 형식 표준화
- [ ] SBOM을 컨테이너 이미지와 함께 OCI 레지스트리에 첨부(Attach)
- [ ] Grype/Snyk으로 SBOM 기반 CVE 스캔 -> 임계치 초과 시 배포 차단
- [ ] SLSA Level 2 이상 달성: 빌드 서비스 분리, Provenance 자동 생성
- [ ] VEX(Vulnerability Exploitability eXchange)로 오탐(False Positive) 관리

**안티패턴**
- ❌ SBOM을 생성만 하고 배포·모니터링에 활용하지 않음 -> 형식적 규제 대응
- ❌ 빌드 환경을 개발자 로컬에서 실행 -> SLSA Level 0, 출처 증명 불가
- ❌ transitive(간접) 의존성을 SBOM에 포함하지 않음 -> 숨은 취약점 미탐지
- ❌ SBOM 업데이트 주기가 릴리스와 불일치 -> 최신성 보장 실패

- 📢 섹션 요약 비유: 성분표를 만들어 놓고 서랍에 넣어두면, 리콜(취약점)이 발생해도 어떤 제품에 해당 성분이 있는지 찾을 수 없다.

## Ⅴ. 기대효과 및 결론

소프트웨어 공급망 보안은 "내가 만든 코드"뿐 아니라 "내가 가져다 쓴 모든 것"까지 책임지는 체계다. SBOM·SLSA·Sigstore를 CI/CD에 통합하면 공급망 공격의 영향을 즉시 파악하고, 규제 요구사항을 자동으로 충족하며, 소프트웨어 신뢰성을 증명할 수 있다. "Trust but Verify"에서 "Verify Everything"으로의 전환이 공급망 보안의 핵심이다.

- 📢 섹션 요약 비유: 식품 공장이 모든 원재료의 출처·검사 이력·성분표를 투명하게 관리하면, 식품 사고가 나도 즉시 원인을 추적하고 리콜할 수 있다.

### 📈 관련 키워드 및 발전 흐름도

```text
수동 라이선스 확인
  -> SCA 도구(Snyk, OWASP Dependency-Check)
    -> SBOM 표준화(SPDX, CycloneDX)
      -> SLSA 빌드 출처 증명
        -> VEX 취약점 영향 분석
          -> 자동화된 공급망 보안 플랫폼
```

### 👶 어린이를 위한 3줄 비유 설명

1. SBOM은 과자 봉지 뒷면의 성분표처럼, 이 프로그램이 어떤 재료(라이브러리)로 만들어졌는지 적어둔 목록이에요.
2. 공급망 보안은 과자 공장에 나쁜 재료가 섞이지 않도록 모든 재료의 출처를 확인하는 것이에요.
3. Sigstore 서명은 과자 봉지의 봉인 스티커처럼, 누군가 몰래 열어서 뭔가를 넣지 않았다는 것을 보증해줘요.
