## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 제로 트러스트 마이크로세그멘테이션은 네트워크 위치나 VLAN 경계가 아니라 **사용자, 단말, 워크로드, 행위 맥락**을 기준으로 최소 권한 통신 정책을 강제하는 세분화 보안 아키텍처다.
> 2. **가치**: 침해가 발생해도 동서 트래픽의 횡적 이동을 차단하여 랜섬웨어 확산, 계정 탈취 후 내부 이동, 클라우드 워크로드 오남용의 피해 반경을 줄인다.
> 3. **판단 포인트**: 정책을 너무 촘촘하게 만들면 운영 장애가 늘고, 너무 느슨하면 제로 트러스트 효과가 사라진다. 관찰 기반 정책 생성과 단계적 차단 전환이 핵심이다.

---

## I. 개요 및 필요성

전통적 네트워크 보안은 외부와 내부를 나누고, 방화벽 안쪽을 비교적 신뢰하는 방식이었다. 그러나 클라우드, 원격 근무, SaaS, 컨테이너, API 연계가 늘면서 내부망 자체가 더 이상 신뢰 경계가 될 수 없게 되었다. 한 계정이나 서버가 침해되면 동일 서브넷, 동일 보안그룹, 동일 클러스터 안의 자산으로 빠르게 이동할 수 있기 때문이다.

마이크로세그멘테이션은 이 문제를 워크로드 단위의 정책으로 해결한다. `업무 시스템 A의 API 서버는 DB 서버의 5432 포트에만 접근`, `CI 러너는 빌드 아티팩트 저장소에만 접근`, `관리자 단말은 PAM을 거쳐야만 운영 서버에 접근`처럼 통신 허용 조건을 작게 정의한다. 제로 트러스트는 여기에 지속 인증, 디바이스 상태, 위험 점수, 세션 검증을 결합한다.

```text
[Zero Trust Microsegmentation]

Identity / Device / Risk
          |
          v
+------------------+       +------------------+
| Policy Decision  | ----> | Policy Enforcer  |
| IdP, ZTNA, PDP   |       | Agent, eBPF, FW   |
+------------------+       +------------------+
          |                         |
          v                         v
+------------------+       +------------------+
| Workload A       | <---> | Workload B       |
| only required    |       | allowed ports    |
+------------------+       +------------------+

허용 기본값: deny by default
정책 단위: identity + workload + protocol + context
```

## II. 아키텍처 및 핵심 원리

마이크로세그멘테이션은 네트워크 장비 하나로 끝나는 기능이 아니다. 자산 식별, 트래픽 관찰, 정책 생성, 집행, 예외 처리, 감사 로그가 하나의 운영 흐름으로 연결되어야 한다.

| 구성 요소 | 역할 | 대표 구현 |
| :--- | :--- | :--- |
| 자산/워크로드 식별 | 서버, 컨테이너, 사용자, 서비스 계정의 속성 수집 | CMDB, CSPM, Kubernetes labels, IAM |
| 트래픽 관찰 | 실제 통신 흐름과 의존성 파악 | NetFlow, eBPF, service mesh telemetry |
| 정책 결정 지점 | 접근 허용 여부 판단 | ZTNA PDP, IAM policy engine, OPA |
| 정책 집행 지점 | 허용/차단을 실제 적용 | host agent, security group, NACL, CNI, service mesh |
| 감사/검증 | 차단 효과와 운영 영향 확인 | SIEM, UEBA, policy simulation |

핵심 원칙은 `default deny`, `least privilege`, `continuous verification`, `blast radius reduction`이다. 처음부터 차단 모드로 들어가면 업무 장애가 커지므로 보통 `observe -> recommend -> monitor -> enforce` 순서로 진행한다.

## III. 비교 및 연결

| 구분 | VLAN/서브넷 분리 | 마이크로세그멘테이션 | ZTNA/SASE |
| :--- | :--- | :--- | :--- |
| 기준 | 네트워크 위치 | 워크로드/ID/태그 | 사용자와 애플리케이션 접근 |
| 세밀도 | 낮음 | 높음 | 사용자 접근 중심 |
| 클라우드 적합성 | 제한적 | 높음 | 높음 |
| 운영 난이도 | 중간 | 높음 | 중간~높음 |
| 주 효과 | 영역 분리 | 횡적 이동 차단 | 외부/원격 접근 보호 |

Kubernetes에서는 NetworkPolicy, Cilium/eBPF, Istio authorization policy가 핵심 수단이 된다. VM 환경에서는 호스트 에이전트나 클라우드 보안그룹 자동화가 많이 쓰인다. 하이브리드 환경에서는 ZTNA와 결합하여 사용자 접근은 ZTNA가, 워크로드 간 통신은 마이크로세그멘테이션이 담당하는 구조가 적합하다.

## IV. 실무 적용 및 실무자 판단

### 적용 절차

1. 중요 자산과 크라운 주얼 시스템을 식별한다.
2. 2~4주 이상 실제 트래픽을 관찰하여 정상 통신 그래프를 만든다.
3. 업무 소유자와 함께 허용 정책을 검토한다.
4. 낮은 위험 구간부터 모니터링 모드로 배포한다.
5. 차단 모드 전환 후 예외 요청, 정책 만료, 변경 승인 절차를 운영한다.

### 판단 체크리스트

- 정책 소유자가 보안팀만이 아니라 업무/플랫폼팀까지 명확한가?
- 서비스 계정, 배치 작업, 운영 점검 트래픽까지 식별했는가?
- 장애 발생 시 우회 정책과 롤백 절차가 준비되어 있는가?
- 정책 변경 이력이 감사 가능하게 남는가?
- 클라우드 보안그룹, Kubernetes policy, service mesh 정책이 충돌하지 않는가?

### 피해야 할 안티패턴

- IP 주소만으로 정책을 작성해 오토스케일링/컨테이너 환경에서 깨지는 경우
- 관찰 기간 없이 차단 정책을 일괄 배포하는 경우
- 예외 정책을 영구 허용으로 방치하는 경우
- 네트워크팀, 보안팀, 애플리케이션팀 책임 경계가 불명확한 경우

## V. 기대효과 및 결론

제로 트러스트 마이크로세그멘테이션은 침해 자체를 완전히 막는 기술이 아니라, 침해 이후 피해 확산을 제어하는 기술이다. 효과는 방화벽 규칙 수가 아니라 침해 시나리오에서 실제로 이동 가능한 경로가 얼마나 줄었는지로 평가해야 한다.

### 관련 개념 맵

| 개념 | 연결 포인트 |
| :--- | :--- |
| Zero Trust | 신뢰 경계를 위치에서 지속 검증으로 이동 |
| ZTNA | 사용자-애플리케이션 접근 제어 |
| SASE | 네트워크 보안 기능의 클라우드 통합 제공 |
| eBPF | 커널 수준 트래픽 관찰과 집행 |
| Service Mesh | 서비스 간 인증, 인가, 암호화 제어 |
