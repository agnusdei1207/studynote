## 핵심 인사이트 (3줄 요약)

> 1. **본질**: Root of Trust (RoT)는 시스템의 모든 보안 검증이 출발하는 최소 불변 신뢰 앵커로, 더 아래 단계에 의존하지 않고 스스로 신뢰의 시작점을 제공한다.
> 2. **가치**: Secure Boot, Measured Boot, 키 보호, 원격 증명은 모두 "첫 코드는 누가 믿게 만드는가"라는 질문에 답해야 하므로, RoT는 플랫폼 보안 전체의 주춧돌이 된다.
> 3. **판단 포인트**: RoT는 제품명이 아니라 구조 개념이므로, 불변 코드·보호된 키·측정·보고·복구·폐기 정책까지 한 세트로 설계해야 실전 신뢰 체인이 완성된다.

## Ⅰ. 개요 및 필요성

Root of Trust (RoT)는 시스템이 맨 처음 믿고 시작하는 최소한의 하드웨어·펌웨어 기반이다. 운영체제, 부트로더, 펌웨어는 모두 누군가의 검증을 받아야 하지만, 이 검증을 끝없이 거슬러 올라갈 수는 없다. 결국 어느 한 지점에서는 "이 코드는 변경 불가능하며, 이 안의 공개키나 측정 로직은 믿는다"는 기준점이 필요하다.

이 기준점이 없으면 보안 부팅은 껍데기에 그친다. 예를 들어 부트로더를 검증하는 펌웨어 자체가 이미 변조돼 있다면, 그 위에서 수행되는 모든 서명 검사는 의미를 잃는다. 그래서 RoT는 보안 기능 중 하나가 아니라, 다른 보안 기능들이 의미를 갖게 해 주는 전제조건이다.

아래 그림은 검증이 왜 끝없이 재귀될 수 없는지, 그리고 어디에서 RoT가 등장하는지 보여 준다.

```text
+----------------------------------------------------------------------------+
| Trust cannot recurse forever                                               |
+----------------------------------------------------------------------------+
| OS image    <- verified by bootloader                                      |
| Bootloader  <- verified by firmware                                        |
| Firmware    <- verified by Boot ROM + immutable key                        |
|                                                                            |
| The last line has no earlier verifier.                                     |
| That immutable anchor is the Root of Trust.                                |
+----------------------------------------------------------------------------+
```

따라서 RoT의 핵심 질문은 단순하다. "제일 처음 실행되는 코드와 제일 처음 쓰이는 키는 누가 지키는가?" 이 질문에 답하지 못하면 상위 계층 보안은 강해 보여도 실제로는 공중에 떠 있는 구조가 된다.

- **📢 섹션 요약 비유**: RoT는 고층빌딩의 가장 깊은 기초 말뚝과 같다. 위층 설계가 아무리 훌륭해도 첫 말뚝이 흔들리면 전체 건물이 같이 흔들린다.

## Ⅱ. 아키텍처 및 핵심 원리

RoT는 보통 불변 부트 코드, 변경 불가능하거나 엄격히 보호된 키 저장소, 측정 엔진, 그리고 외부 보고 기능으로 구성된다. 불변 부트 코드는 Boot ROM (Read-Only Memory)이나 OTP (One-Time Programmable) 영역에 존재하고, 여기에는 다음 단계 이미지를 검증할 공개키 해시나 정책이 들어 있다. 전원이 켜지면 이 첫 코드가 다음 단계를 검증하고, 필요하면 측정값을 기록하며, 검증이 끝난 코드에만 실행 권한을 넘긴다.

RoT를 더 세분화하면 RoT for Measurement, RoT for Storage, RoT for Reporting으로 나눌 수 있다. Measurement는 무엇이 실행됐는지 측정하고, Storage는 루트 키와 장치 비밀을 보호하며, Reporting은 현재 상태를 외부 검증자에게 증명한다. 이 세 기능이 함께 있어야 보안 부팅, 키 보호, 원격 증명이 하나의 사슬로 이어진다.

| 구성 요소 | 역할 | 대표 구현 예 |
| :-- | :-- | :-- |
| Boot ROM | 첫 번째 실행 코드를 불변 상태로 유지 | CPU (Central Processing Unit) 내부 ROM, 마스크 ROM |
| 보호된 키 저장소 | 공개키 해시, 장치 비밀, 복구 키 보관 | eFuse, OTP, 보안 NVRAM |
| 측정 엔진 | 각 부팅 단계를 해시로 측정 | TPM (Trusted Platform Module)의 PCR (Platform Configuration Register), DICE (Device Identifier Composition 엔진) 기반 파생값 계산 |
| 검증 로직 | 서명·버전·롤백 여부 확인 | Secure Boot, Boot Guard |
| 보고 기능 | 측정 결과를 외부에 전달 | Quote, 원격 증명 토큰 |

아래 그림은 RoT가 부팅과 증명에 개입하는 전형적 흐름이다.

```text
+----------------------------------------------------------------------------+
| RoT-driven boot and remote verification flow                               |
+----------------------------------------------------------------------------+
| Power on                                                                   |
|   -> Boot ROM reads immutable key / hash                                   |
|   -> verify firmware signature                                             |
|   -> measure stage into PCR / log                                          |
|   -> release next-stage execution                                          |
|   -> protected keys become usable only after valid boot                    |
|   -> remote attestation token proves state to a remote verifier            |
+----------------------------------------------------------------------------+
```

이 구조의 본질은 신뢰가 "점프"하지 않고 "계승"된다는 데 있다. 한 단계가 다음 단계를 검증해 신뢰를 넘겨주고, 검증 실패 시에는 부팅 차단·복구 모드 진입·키 비공개 같은 보수적 동작으로 전환한다. 즉 RoT는 단순 저장소가 아니라, 실행 허가와 상태 증명까지 통제하는 정책의 시작점이다.

- **📢 섹션 요약 비유**: RoT는 공항의 첫 출입 심사대와 같다. 여기서 여권과 탑승권이 처음 검증돼야 그다음 보안 검색과 탑승 절차도 의미가 생긴다.

## Ⅲ. 비교 및 연결

RoT는 자주 SRTM (Static Root of Trust for Measurement)과 DRTM (Dynamic Root of Trust for Measurement)으로 구분해 이해한다. SRTM은 전원 인가 직후 첫 코드부터 차례대로 측정과 검증을 시작하는 방식이고, DRTM은 이미 실행 중인 시스템에서도 특정 시점에 새로운 신뢰 구간을 다시 만드는 방식이다.

| 구분 | SRTM | DRTM |
| :-- | :-- | :-- |
| 시작 시점 | 전원 인가 직후 | 런타임 중 특정 시점 |
| 장점 | 구현이 직관적이고 부팅 체인 전체와 잘 맞는다 | 이미 부팅된 환경에서도 신뢰 구간을 재설정할 수 있다 |
| 한계 | 초기 체인이 길면 공격 표면이 넓어진다 | 구현 복잡도와 플랫폼 의존성이 높다 |
| 대표 연결 기술 | Secure Boot, Measured Boot | Intel TXT (Trusted Execution Technology), SKINIT, late launch 계열 |

또 하나 중요한 비교는 RoT 자체와 이를 구현하는 장치의 차이다. TPM은 RoT 기능 일부를 제공하는 칩이고, HSM (Hardware Security Module)은 조직 단위 키 보호 장치이며, TEE (Trusted Execution Environment)는 보호 실행 구역이다. 즉 TPM이나 TEE가 곧 RoT는 아니고, 이들이 RoT의 일부 기능을 맡거나 RoT 위에서 동작한다는 식으로 이해해야 혼동이 줄어든다.

이 관점에서 보면 Secure Boot는 RoT가 검증 체인을 시작하는 방식이고, Measured Boot는 "무엇이 실행됐는가"를 기록하는 방식이며, 원격 증명 (Attestation)은 그 결과를 밖에 보여 주는 방식이다. 세 개는 경쟁 관계가 아니라 RoT가 확장되는 서로 다른 표현이다.

- **📢 섹션 요약 비유**: SRTM은 건물을 지을 때 기초부터 차례대로 검사하는 방식이고, DRTM은 이미 운영 중인 건물 안에 새 보안 구역을 만들며 다시 검문을 시작하는 방식과 같다.

## Ⅳ. 실무 적용 및 실무자 판단

실무에서 RoT는 서버, 노트북, 네트워크 장비, 사물인터넷 장치 모두에 들어간다. 서버에서는 펌웨어 무결성 확인과 원격 증명에 쓰이고, 소비자 기기에서는 Secure Boot와 디스크 키 보호의 출발점이 된다. 제조 현장에서는 출하 시 장치 키를 어떻게 주입할지, 서비스 단계에서는 키 폐기와 복구를 어떻게 처리할지가 RoT 설계의 핵심 이슈다.

### 적용 체크리스트

1. **불변 첫 단계**: 첫 실행 코드가 정말 ROM 또는 이에 준하는 불변 영역에 있는가?
2. <strong>키 보호</strong>: 공개키 해시, 장치 비밀, 복구 키가 일반 플래시와 분리돼 있는가?
3. <strong>폐기 / 회전 정책</strong>: 키 교체, 폐기, 롤백 방지 정책이 준비돼 있는가?
4. **측정과 보고**: 측정 로그와 원격 증명이 실제 운영 시스템과 연결돼 있는가?
5. <strong>복구 경로</strong>: 검증 실패 시 안전한 복구 모드와 현장 복원 절차가 있는가?

### 피해야 할 안티패턴

- 루트 공개키를 업데이트 가능한 일반 플래시에만 저장하는 설계
- Secure Boot만 켜 두고 측정 기록이나 원격 증명은 전혀 연계하지 않는 운영
- 복구 키와 폐기 정책 없이 "변조되면 그냥 벽돌"이 되게 두는 제품 설계

실무 관점에서는 RoT를 "가장 아래에 있는 믿음"이라고만 설명하면 절반이다. 나머지 절반은 그 믿음을 어떤 하드웨어에 고정하고, 어떻게 상위 단계 검증으로 전달하며, 실패 시 어떤 안전 동작을 하게 만드는가를 적는 것이다. 결국 RoT는 하드웨어, 키 관리, 부팅 정책, 운영 복구가 만나는 접점이다.

- **📢 섹션 요약 비유**: RoT 설계는 집 현관문 자물쇠만 튼튼하게 다는 일이 아니다. 비상 열쇠를 어디 둘지, 잃어버리면 어떻게 바꿀지, 문이 억지로 열렸을 때 어떻게 알릴지까지 함께 정해야 진짜 안전한 집이 된다.

## Ⅴ. 기대효과 및 결론

RoT를 올바르게 설계하면 부팅 무결성, 키 보호, 장치 신원, 원격 증명이 하나의 체계로 묶인다. 그 결과 악성 펌웨어 주입, 공급망 변조, 무단 부팅 이미지 실행 같은 위협을 초기 단계에서 차단할 수 있다. 특히 클라우드와 엣지 환경에서는 "이 장치가 정말 내가 허용한 상태인가"를 말할 수 있게 해 준다는 점이 크다.

하지만 RoT는 타협할 수 없는 단일 실패 지점이기도 하다. 루트 키가 잘못 주입되거나 첫 단계 코드가 뚫리면 위 체계 전체가 함께 붕괴한다. 그래서 앞으로의 방향은 Silicon RoT, DICE (Device Identifier Composition 엔진), 기밀 컴퓨팅 증명처럼 더 작은 신뢰 기저를 만들고, 그 상태를 자동으로 증명하는 방향에 가깝다. 결론적으로 RoT는 <strong>보안 기능 하나가 아니라, 모든 보안 기능이 기대는 첫 약속</strong>으로 기억해야 한다.

- **📢 섹션 요약 비유**: RoT는 반 전체가 믿는 담임선생님의 출석부와 같다. 출석부 자체가 틀리면 이후의 출결, 성적, 상벌 기록도 모두 함께 흔들린다.

### 📌 관련 개념 맵

| 개념 | 연결 포인트 |
| :-- | :-- |
| Boot ROM | 불변 첫 코드로서 RoT의 가장 전형적인 구현이다. |
| eFuse / OTP | 루트 공개키 해시와 장치 비밀을 영구 저장하는 대표 매체다. |
| Secure Boot | RoT가 다음 단계 코드의 서명을 검증하며 신뢰를 전달하는 구조다. |
| Measured Boot | 무엇이 실행됐는지 해시로 기록해 사후 증명에 활용한다. |
| TPM (Trusted Platform Module) | 측정, 저장, 보고 기능 일부를 칩 형태로 제공한다. |
| Attestation | RoT에서 시작된 측정 결과를 외부 검증자에게 증명하는 절차다. |

### 📈 관련 키워드 및 발전 흐름도

```text
불변 부트 코드
        |
        v
Root of Trust (RoT)
        |
        +---------> Secure Boot
        |
        +---------> Measured Boot
                     |
                     v
Attestation
        |
        v
Silicon RoT · DICE · 클라우드 플랫폼 신뢰 검증
```

이 흐름은 "첫 신뢰 앵커"에서 "부팅 체인 검증"으로, 다시 "원격에서 확인 가능한 플랫폼 신뢰"로 확장되는 구조를 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. RoT는 컴퓨터가 맨 처음 믿는 약속장이에요.
2. 그 약속장이 진짜여야 그다음에 읽는 숙제장과 시험지도 믿을 수 있어요.
3. 그래서 컴퓨터는 제일 처음 약속장을 아무나 못 고치게 아주 깊숙한 곳에 숨겨 두어요.
