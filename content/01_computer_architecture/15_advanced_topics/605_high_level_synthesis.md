## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 고수준 합성은 C/C++·SystemC 같은 알고리즘 모델을 레지스터 전송 수준 (Register Transfer Level, RTL) 회로로 바꾸는 컴파일러형 설계 기법이며, 실제 결과물은 코드 문장보다도 연산 의존성과 메모리 구조가 좌우한다.
> 2. **가치**: 사람이 상태기계와 배선을 일일이 쓰는 시간을 줄여 설계 반복 속도를 높이고, 같은 알고리즘에서 파이프라인 깊이·병렬도·메모리 뱅킹을 빠르게 바꿔 보며 아키텍처를 탐색하게 해 준다.
> 3. **판단 포인트**: HLS는 "소프트웨어를 바로 칩으로 바꾸는 마법"이 아니라 규칙적인 루프와 데이터플로에 강한 도구이므로, 루프 의존성·메모리 포트 수·인터페이스 제약을 읽지 못하면 수동 RTL보다 느리고 큰 회로도 쉽게 나온다.

---

## Ⅰ. 개요 및 필요성

고수준 합성은 알고리즘을 먼저 기술하고, 그 알고리즘을 만족하는 하드웨어 구조를 도출하는 설계 방식이다. 전통적인 하드웨어 설명 언어 (Hardware Description Language, HDL) 기반 설계는 신호, 상태, 핸드셰이크, 레지스터 배치를 설계자가 직접 적어야 하므로, 이미지 처리·디지털 신호 처리·인공지능 가속처럼 계산 핵심은 명확하지만 구조 실험이 잦은 영역에서 생산성 병목이 컸다. HLS는 이 간극을 줄이기 위해 등장했다.

왜 필요한지도 명확하다. 알고리즘이 바뀔 때마다 레지스터 전달 순서와 상태 전이를 전부 다시 손보는 것은 너무 느리다. 반면 C 모델은 수정과 검증이 빠르므로, "기능을 먼저 맞추고 하드웨어 구조는 제약으로 유도"하는 쪽이 반복 설계에 유리하다. 특히 파일드 프로그래머블 게이트 배열 (Field-Programmable Gate Array, FPGA) 기반 가속기에서는 여러 후보 구조를 빠르게 시험할 수 있어 HLS의 체감 가치가 크다.

이 그림은 수동 RTL과 HLS의 차이를 "누가 구조를 직접 책임지는가" 관점에서 보여 준다.

```text
+----------------------------------------------------------------------------+
|                   Manual RTL vs HLS: who builds the structure?            |
+----------------------------------------------------------------------------+
| Algorithm idea                                                            |
|     |                                                                     |
|     +- Manual RTL -> engineer writes states, registers, handshakes        |
|     |                                                                     |
|     +- HLS        -> engineer writes behavior + constraints               |
|                     tool builds schedule, datapath, controller, interface |
|                                                                           |
| Result quality still depends on dependency graph and memory access shape. |
+----------------------------------------------------------------------------+
```

즉 HLS의 핵심은 RTL을 없애는 것이 아니라, RTL을 더 늦은 단계에서 자동 생성하게 만드는 것이다. 사람이 고민해야 할 축이 배선 세부에서 <strong>병렬도와 데이터 이동 구조</strong>로 올라간다고 이해하면 정확하다.

- **📢 섹션 요약 비유**: 전통적 RTL이 벽돌 한 장까지 직접 쌓는 수작업 건축이라면, HLS는 건물 용도와 하중 조건을 넣고 모듈 배치를 자동 설계하는 공장식 건축에 가깝다. 다만 방 배치를 잘못 잡으면 자동으로 지어도 불편한 건물밖에 안 나온다.

## Ⅱ. 아키텍처 및 핵심 원리

HLS 도구는 코드를 그냥 "번역"하지 않는다. 먼저 연산 사이의 의존성을 읽고, 이어서 어느 연산을 몇 번째 사이클에 둘지 정하고, 그다음 어떤 연산기를 몇 개 둘지 배정하며, 마지막으로 스트리밍·메모리 맵 같은 인터페이스를 합성한다. 그래서 HLS 결과를 이해하려면 구문보다 <strong>스케줄링, 자원 바인딩, 메모리 아키텍처</strong>를 먼저 봐야 한다.

| 단계 | HLS가 하는 일 | 설계자가 봐야 할 질문 |
| :--- | :--- | :--- |
| 전처리/분석 | 루프, 조건문, 배열 접근을 해석해 제어-데이터 흐름 그래프 (Control Data Flow Graph, CDFG)를 만든다. | 루프 의존성과 메모리 alias가 명확한가? |
| 스케줄링 | 연산을 클럭 사이클에 배치한다. | 목표 주기 안에 들어오는가, 루프의 개시 간격 (Initiation Interval, II)이 얼마인가? |
| 자원 할당/바인딩 | 곱셈기, 가산기, 메모리 포트, 레지스터를 몇 개 둘지 결정한다. | 병렬도를 늘릴수록 면적이 얼마나 커지는가? |
| 메모리 구조화 | 배열 분할, 버퍼링, 로컬 저장소 배치를 수행한다. | 계산보다 메모리 포트가 먼저 병목이 되지 않는가? |
| 인터페이스 합성 | 함수 입출력을 스트림, 메모리 맵, 핸드셰이크 포트로 바꾼다. | 시스템 나머지 블록과 backpressure를 안전하게 주고받는가? |

이 그림은 HLS 내부 흐름과 결과 보고서에서 봐야 할 포인트를 한 번에 묶은 것이다.

```text
+----------------------------------------------------------------------------+
|                    HLS flow: behavior -> structure -> reports             |
+----------------------------------------------------------------------------+
| C/C++ / SystemC                                                           |
|      |                                                                    |
|      v                                                                    |
|   CDFG analysis                                                           |
|      |                                                                    |
|      +- schedule with target clock                                        |
|      +- bind operations to arithmetic units                               |
|      +- shape memories / banks / local buffers                            |
|      +- synthesize interfaces                                             |
|      |                                                                    |
|      v                                                                    |
|   RTL + latency report + II report + resource report                      |
+----------------------------------------------------------------------------+
```

실무에서 많이 쓰는 제어 수단도 결국 이 흐름에 대응한다. 파이프라인은 `II`를 줄여 처리량을 올리고, 언롤은 연산기를 복제해 병렬도를 높이며, 배열 분할은 메모리 포트 충돌을 줄인다. 예를 들어 목표 주파수가 같다면 처리량은 대략 `f_clk / II`에 비례하므로, II가 4에서 1로 내려가면 같은 클럭에서도 체감 성능이 크게 바뀐다. 반대로 메모리 포트가 1개뿐이면 언롤을 많이 걸어도 연산기가 데이터를 못 받아 놀 수 있다.

그래서 좋은 HLS 설계는 코드 문법보다 데이터 이동을 먼저 정리한다. "연산을 몇 개 복제할까?"보다 "그 연산기들이 매 사이클 먹을 데이터를 어디서 어떻게 공급할까?"가 더 자주 승부를 가른다.

- **📢 섹션 요약 비유**: HLS는 요리 레시피를 자동화 공장으로 바꾸는 감독과 같다. 조리사 수를 늘리는 것만으로는 부족하고, 재료 창고와 컨베이어가 그 속도를 따라와야 진짜 생산량이 오른다.

## Ⅲ. 비교 및 연결

HLS의 경계는 수동 RTL과 소프트웨어 실행 사이에 있다. 소프트웨어 컴파일러는 같은 명령 집합 위에서 코드를 더 빠르게 배치하지만, HLS는 아예 실행 하드웨어 구조 자체를 만든다. 반면 수동 RTL은 가장 세밀한 제어가 가능하지만, 구조 변경 비용이 크다. 따라서 HLS는 <strong>유연성과 최적화 자유도 사이의 절충점</strong>으로 보는 것이 맞다.

| 관점 | 소프트웨어 컴파일 | HLS | 수동 RTL |
| :--- | :--- | :--- | :--- |
| 바꾸는 대상 | 명령어 배치 | 데이터패스와 제어 구조 | 신호와 레지스터 세부 |
| 강점 | 개발 속도, 디버깅 용이 | 설계 탐색 속도, 반복성 | 미세 타이밍·면적 최적화 |
| 약점 | 범용 프로세서 한계 | 결과가 메모리 구조와 pragma 품질에 민감 | 변경 비용과 검증 비용이 큼 |
| 잘 맞는 블록 | 범용 제어·불규칙 소프트웨어 | 규칙적 계산 커널, 스트리밍 가속 | 초정밀 인터페이스, 타이밍 민감 제어 |

이 비교가 중요한 이유는 HLS가 모든 블록을 대체하지 않기 때문이다. 예를 들어 메모리 컨트롤러, 초고속 직렬 링크, 복잡한 클럭 도메인 교차 (Clock Domain Crossing, CDC) 경계는 여전히 수동 RTL이 더 명확한 경우가 많다. 반대로 행렬 곱, 필터, 비디오 파이프라인 같은 규칙적 커널은 HLS가 훨씬 빠르게 구조 탐색을 돌릴 수 있다.

또한 HLS는 그 자체로 끝나는 기술이 아니다. HLS로 만든 연산 커널을 동적 재구성 영역에 올리거나, 주변 입출력은 수동 RTL로 감싸고, 스트림 경계는 비동기 FIFO (Asynchronous First-In First-Out, Async FIFO)로 완충하는 식으로 다른 주제들과 자연스럽게 연결된다. 즉 HLS는 "칩 전체를 다 만드는 만능기"가 아니라, <strong>계산 중심 블록을 빠르게 설계하는 상위 레벨 진입점</strong>이다.

- **📢 섹션 요약 비유**: HLS는 맞춤 정장을 손바느질로 전부 만드는 것과 기성복만 입는 것의 중간쯤이다. 몸에 맞는 큰 틀은 빠르게 잡아 주지만, 단추 위치까지 극단적으로 다듬는 일은 여전히 장인의 손이 필요할 수 있다.

## Ⅳ. 실무 적용 및 실무자 판단

실무에서 HLS가 가장 잘 맞는 곳은 계산 패턴이 반복되고, 요구사항이 자주 바뀌며, "정답 구조 하나"보다 "후보 구조 여러 개"를 빨리 비교해야 하는 환경이다. 영상 전처리, 통신 필터, 압축/복호화, 행렬 연산, 센서 융합 가속기가 대표적이다. 이 경우 C 모델 검증과 HLS 보고서를 연결해 빠르게 설계를 돌릴 수 있다.

반대로 포인터 추적이 심한 불규칙 알고리즘, 동적 메모리 할당, 재귀, 복잡한 예외 처리, 클럭·리셋 경계가 많은 제어 블록은 HLS 효율이 급격히 떨어질 수 있다. 이런 코드는 합성은 되더라도 면적이 비대해지거나 II가 커져 기대만큼 빨라지지 않는다. 따라서 학습 정리에서도 "HLS 사용 여부"는 생산성 찬양이 아니라, <strong>패턴 규칙성·메모리 접근·인터페이스 제약</strong>을 근거로 판단해야 한다.

### 적용 판단 체크리스트

1. 루프 간 의존성을 끊어 파이프라인이 실제로 가능하게 만들었는가?
2. 언롤한 만큼 읽기/쓰기 포트와 로컬 버퍼를 마련했는가?
3. HLS 추정 지연시간이 배치배선 후에도 유지될 현실적 타이밍 목표인가?
4. 스트리밍 입력의 backpressure와 메모리 대역폭을 함께 모델링했는가?
5. C 시뮬레이션, 공동 시뮬레이션 (co-simulation), 실제 RTL 검증이 같은 골든 동작을 가리키는가?

### 피해야 할 안티패턴

- 소프트웨어 코드를 거의 그대로 넣고 pragma만 잔뜩 붙여 성능이 날 것이라 기대하는 접근
- 계산 병렬도만 높이고 메모리 병목을 방치하는 설계
- HLS 보고서만 믿고 후단 배치배선 결과를 보지 않는 판단
- 시스템 전체 인터페이스보다 커널 내부 성능 수치만 보는 평가

결국 HLS의 실무 포인트는 "코드가 합성되느냐"가 아니라, "합성된 구조가 시스템 안에서 균형 잡힌 가속기가 되느냐"다. 성능 보고서, 메모리 맵, 주변 인터페이스까지 같이 읽어야 진짜 판단이 된다.

- **📢 섹션 요약 비유**: 요리 로봇을 도입한다고 바로 맛집이 되지는 않는다. 재료 동선, 조리 순서, 손님 주문 흐름을 같이 설계해야 로봇이 진짜 힘을 발휘한다.

## Ⅴ. 기대효과 및 결론

HLS를 잘 쓰면 설계 반복 속도가 빨라지고, 같은 알고리즘을 여러 자원 예산과 주파수 목표에 맞춰 빠르게 재구성할 수 있다. 이는 개발 기간 단축뿐 아니라, 팀이 더 많은 구조 후보를 실제 수치로 비교할 수 있게 해 준다는 점에서 가치가 크다. 특히 FPGA 프로토타이핑에서 빠르게 유효 구조를 찾은 뒤 주문형 반도체 (Application-Specific Integrated Circuit, ASIC) 방향으로 넘기는 흐름과도 잘 맞는다.

한계도 분명하다. 생성된 RTL이 항상 최적은 아니며, 메모리 구조를 잘못 잡으면 수동 RTL보다 비효율적일 수 있다. 또한 디버깅 관점에서는 C 코드, HLS 중간 보고서, 생성 RTL, 실제 배치배선 결과를 함께 봐야 하므로 추상화가 올라간 만큼 관찰 계층도 늘어난다. 앞으로는 자동 pragma 탐색, 기계학습 기반 설계 공간 탐색, 도메인 특화 언어와의 결합이 더 중요해질 가능성이 크다.

결론적으로 HLS는 <strong>"소프트웨어를 칩으로 바꾸는 번역기"가 아니라, 알고리즘을 하드웨어 아키텍처 후보군으로 변환하는 설계 컴파일러</strong>로 기억하는 것이 가장 정확하다. 이 관점을 잡으면 왜 코드 품질보다 의존성, 버퍼링, 병렬도가 더 중요하게 다뤄지는지 자연스럽게 이해된다.

- **📢 섹션 요약 비유**: HLS는 만능 자동 통역기가 아니라, 회의 내용을 들으면 곧바로 조직도를 짜 주는 운영 설계자에 가깝다. 말을 옮기는 것보다 누가 어떤 일을 동시에 할지를 정하는 능력이 더 중요하다.

### 📌 관련 개념 맵

| 개념 | 연결 포인트 |
| :--- | :--- |
| 레지스터 전송 수준 (Register Transfer Level, RTL) | HLS가 최종적으로 생성하는 하드웨어 기술 계층이다. |
| 제어-데이터 흐름 그래프 (Control Data Flow Graph, CDFG) | HLS가 코드의 연산 의존성을 하드웨어적으로 해석하는 핵심 중간 표현이다. |
| 개시 간격 (Initiation Interval, II) | 파이프라인 처리량을 읽을 때 가장 먼저 보는 핵심 지표다. |
| 배열 분할 (Array Partition) | 병렬 연산기를 먹이는 메모리 포트를 확보하는 대표 기법이다. |
| 데이터플로 (Dataflow) | 함수/루프를 스트림으로 연결해 블록 간 중첩 실행을 만드는 최적화 방식이다. |
| 파일드 프로그래머블 게이트 배열 (Field-Programmable Gate Array, FPGA) | HLS의 빠른 설계 탐색과 프로토타이핑이 가장 활발하게 일어나는 대표 플랫폼이다. |

### 📈 관련 키워드 및 발전 흐름도

```text
수동 RTL 중심 설계
      |
      v
C 모델 기반 기능 검증
      |
      v
HLS 스케줄링 · 자원 바인딩
      |
      v
파이프라인 · 언롤 · 데이터플로 최적화
      |
      v
FPGA 가속기 설계 공간 탐색
      |
      v
도메인 특화 언어 · 자동 튜닝 기반 하드웨어 생성
```

이 흐름은 하드웨어 설계가 "신호를 직접 쓰는 단계"에서 출발해, 이제는 알고리즘 모델을 여러 하드웨어 후보로 빠르게 펼쳐 보는 방향으로 진화하고 있음을 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. 예전에는 장난감 공장을 만들려면 기계 나사 하나까지 사람이 직접 그려야 했어요.
2. HLS는 "이 장난감은 이렇게 움직여"라고 설명하면, 기계 배치를 자동으로 짜 주는 똑똑한 설계 도우미예요.
3. 하지만 재료 창고와 길을 잘못 잡으면 자동으로 지어도 느린 공장이 되니, 똑똑한 계획은 여전히 사람이 세워야 해요.
