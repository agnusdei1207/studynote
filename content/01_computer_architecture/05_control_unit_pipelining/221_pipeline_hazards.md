# 📖 【암기용】 개념 완전 이해

> 목적: 파이프라인 해저드를 처음 봐도 완벽히 이해하게 만든다. 시험 답안 양식이 아니라, 이해를 위한 친절한 설명이다.

## 한눈에
- **정의**: 명령어를 겹쳐 실행할 때 흐름이 깨지는 충돌 현상
- **왜 필요한가**: 파이프라인은 매 클럭 결과 1개를 내야 이상적인데, 실제 명령어는 서로 의존해서 그 흐름이 자주 막힌다. 이 "막힘"을 이해해야 CPU 성능 한계를 설명할 수 있다.
- **핵심 직관**: 공장 컨베이어처럼 명령어를 흘리는데, 앞 작업 결과를 뒤 작업이 기다리거나 같은 도구를 동시에 쓰려 하면 라인이 멈춘다.

## 깊이 이해
- **배경·문제의식**: 5단 파이프라인(IF·ID·EX·MEM·WB)은 이론상 5배 빠르지만, 명령어가 독립적일 때만 그렇다. 현실 코드는 의존성·분기가 많아 실제 CPI가 1에 도달하지 못한다.
- **작동 원리**: 해저드는 3종이다. ① **구조적** — 한 자원(메모리 포트·ALU)을 둘이 동시 요구. ② **데이터** — 앞 명령 결과를 뒤 명령이 즉시 필요(RAW가 대표). ③ **제어** — 분기 결과가 안 정해져 다음에 뭘 가져올지 모름. 각각 Stall(멈춤)·Forwarding(결과를 EX단계로 바로 전달)·Flush(잘못 가져온 명령 버림)로 대응한다.
- **비유**: 요리사 5명이 차례로 한 접시를 만드는데, 2번 요리사가 1번의 소스를 기다리면(데이터) 줄이 선다. 칼 하나를 둘이 쓰려 하면(구조적) 한 명이 기다린다. 다음 주문이 뭔지 모르면(제어) 일단 추측해 만들다 틀리면 버린다(Flush).
- **구체 예시**: `ADD R1,R2,R3` 직후 `SUB R4,R1,R5`는 R1을 즉시 써서 RAW 해저드. 포워딩 없으면 3사이클 Stall, 포워딩으로 0사이클.
- **흔한 오해·주의점**: "단(stage)을 늘리면 무조건 빨라진다"는 틀렸다. 단이 깊을수록 분기 예측 실패 시 버리는 명령이 많아져 제어 해저드 페널티가 커진다.

## 연결 개념
- 분기 예측(Branch Prediction) — 제어 해저드 해소의 핵심
- 데이터 포워딩(Forwarding) — 데이터 해저드 해소의 핵심
- 비순차 실행(OoO)·레지스터 리네이밍 — WAR/WAW 해저드 제거

# 📝 【답안용】 시험 답안 템플릿

> 목적: 시험장에서 25분에 그대로 쓰는 답안 양식. 작성방식(추상표현 금지·수치·도식·문제유형 전환)을 엄격히 지킨다.

## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 파이프라인 해저드 (Pipeline Hazards)는 여러 명령어를 겹쳐 흘려보낼 때 자원 충돌·데이터 의존성·분기 불확실성으로 이상적인 흐름이 깨지는 병목 현상이다.
> 2. **가치**: 실제 CPI (Cycles Per Instruction)는 단계 수보다 스톨(Stall)·버블(Bubble)·플러시(Flush)를 얼마나 줄이느냐에 의해 결정된다.
> 3. **판단 포인트**: 구조적·데이터·제어 해저드는 원인이 다르므로 자원 복제·포워딩·분기 예측·컴파일러 스케줄링을 각각 다른 처방으로 적용해야 한다.

---

## Ⅰ. 개요 및 필요성

파이프라인 해저드는 명령어 파이프라이닝 (Instruction Pipelining)에서 여러 명령어가 동시에 흐를 때 정상 진행을 방해하는 충돌 조건이다. 5단 파이프라인은 매 클럭마다 결과를 하나씩 내야 하지만, 실제 프로그램은 자원 공유·데이터 의존·분기로 인해 이 흐름이 깨진다. 해저드가 많으면 고주파 CPU도 실제 성능이 기대를 밑돌기 때문에, 파이프라인 설계의 핵심은 단계 분리보다 충돌 방지 메커니즘 설계에 있다.

---

## Ⅱ. 구조 및 구성요소

```text
┌─────────────────────────────────────────────────────────┐
│              파이프라인 해저드 분류 구조                  │
├──────────────┬──────────────────┬───────────────────────┤
│  구조적 해저드 │   데이터 해저드   │    제어 해저드          │
│ (Structural) │   (Data)         │    (Control)           │
│              │  RAW / WAR / WAW │    분기·점프·예외       │
│  자원 충돌   │  데이터 의존성    │   다음 PC 불확실        │
└──────────────┴──────────────────┴───────────────────────┘
```

| 구성요소 | 정의 | 주요 원인 |
|:---|:---|:---|
| 구조적 해저드 (Structural) | 두 명령어가 같은 하드웨어 자원을 동시에 요구 | 단일 메모리 포트, 단일 ALU |
| 데이터 해저드 (Data) | 선행 명령어 결과를 후속 명령어가 즉시 필요 | RAW·WAR·WAW 의존성 |
| 제어 해저드 (Control) | 분기·점프로 인해 다음 인출 주소가 불확실 | 조건 분기·예외·인터럽트 |

> 요약: 해저드는 자원(구조적)·데이터 의존(데이터)·흐름 불확실(제어) 세 종류로 분류되며, 각 종류는 발생 원인과 해소 방법이 다르다.

---

## Ⅲ. 동작원리 및 흐름도

```text
명령어 IF → ID → EX → MEM → WB
                │
         해저드 감지
         ┌──────┴──────┐
    구조적 해저드    데이터 해저드    제어 해저드
         │               │               │
    Stall 삽입    포워딩 or Stall    Flush + 예측
         │               │               │
    다음 클럭 재시도   정상 진행    예측 맞으면 진행
                                   틀리면 Flush
```

| 단계 | 처리 내용 | 해소 기법 |
|:---:|:---|:---|
| 1 | 명령어 인출 (IF) — 순차 또는 예측 주소 | 분기 예측 (Branch Prediction) |
| 2 | 디코드 (ID) — 의존성 감지 | 포워딩 경로 판단, Stall 발행 |
| 3 | 실행 (EX) — 자원 사용 충돌 감지 | 자원 복제, 파이프라인 인터록 |
| 4 | 메모리 (MEM) — Load-Use 충돌 | Load-Use Stall, 컴파일러 스케줄링 |
| 5 | 분기 결과 확정 (WB 이전) — 예측 오류 시 Flush | 빠른 분기 판정, BTB (Branch Target Buffer) |

> 요약: 해저드는 ID 단계 의존성 감지 → 포워딩/스톨 삽입 → 분기 확정 후 Flush 순서로 통제되며, 대부분의 해소는 하드웨어 포워딩과 컴파일러 스케줄링의 협력으로 이뤄진다.

---

## Ⅳ. 특징

| 구분 | 구조적 해저드 | 데이터 해저드 | 제어 해저드 |
|:---|:---|:---|:---|
| 발생 조건 | 자원 공유 | RAW·WAR·WAW 의존 | 분기·점프·예외 |
| 주요 해소법 | 자원 복제, Stall | 데이터 포워딩, Stall | 분기 예측, Flush |
| 성능 영향 | 낮음 (설계로 제거 가능) | 중간 (포워딩으로 대부분 제거) | 높음 (예측 실패 시 수 클럭 손실) |
| 실무자 포인트 | 분리 I-Cache/D-Cache | RAW는 포워딩, WAR/WAW는 레지스터 리네이밍 | 동적 예측 vs 정적 예측 트레이드오프 |

> 요약: 제어 해저드가 성능 영향이 가장 크며, 현대 CPU는 동적 분기 예측(BTB·BHT)으로 95% 이상 적중률을 달성하여 플러시 빈도를 최소화한다.

---

## Ⅴ. 실무 적용 및 결론

**적용 방안 3개:**
1. 데이터 해저드: EX/MEM·MEM/WB 포워딩 경로 구현으로 RAW 스톨을 3사이클→0사이클로 제거, Load-Use만 1사이클 잔존
2. 제어 해저드: 2비트 포화 카운터 BHT(Branch History Table) + BTB로 분기 적중률 95% 이상 확보, 플러시 빈도 최소화
3. 컴파일러 협력: 명령어 재배치(Instruction Scheduling)·지연 분기(Delayed Branch)로 잔여 버블을 정적으로 흡수

**결론 (2줄):**
- 실무자 판단: 파이프라인 성능 = IPC × 클럭 주파수이며, 단(stage) 수 5단 이하면 정적 예측, 15단 이상이면 동적 예측+OoO를 선택한다
- 향후 방향: Meltdown·Spectre 이후 투기적 실행의 보안 취약점이 부각되어, 해저드 해소와 보안 격리(예: IBRS, Retpoline)를 동시에 설계해야 한다
