## 핵심 인사이트 (3줄 요약)

> 1. **본질**: CAA (Certification Authority Authorization)는 도메인 소유자가 DNS (Domain Name System)에 "어떤 인증기관 (CA, Certificate Authority)만 내 인증서를 발급할 수 있는가"를 선언하는 정책 레코드다.
> 2. **가치**: 신뢰 저장소에 많은 CA가 들어 있는 웹 PKI (Public Key Infrastructure) 환경에서, 도메인 소유자가 허용한 기관 외의 오발급 가능성을 발급 직전에 줄여 주는 저비용 예방 통제다.
> 3. **판단 포인트**: CAA는 CT (Certificate Transparency)처럼 사후 공개 감시를 대체하지 않으며, 정확한 DNS 운영과 DNSSEC (Domain Name System Security Extensions) 같은 무결성 보호가 함께 갈 때 효과가 커진다.

---

## Ⅰ. 개요 및 필요성

CAA는 인증서 발급 권한을 도메인 소유자가 명시적으로 제한하는 DNS 정책이다. 웹 브라우저는 수많은 공인 CA를 신뢰하지만, 도메인 소유자는 보통 그중 일부만 사용한다. 문제는 공격자나 운영 실수가 엉뚱한 CA를 통해도 인증서 발급 시도로 이어질 수 있다는 점이다.

이 개념이 필요해진 배경은 웹 PKI의 약한 고리 문제다. 어떤 도메인이 DigiCert만 쓰더라도, 브라우저 신뢰 저장소에 있는 다른 CA가 잘못된 검증으로 인증서를 발급하면 사용자 입장에서는 여전히 위험하다. CAA는 이 상황에서 "도메인 주인이 허용한 기관만 발급하라"는 정책을 DNS에 공개해, 발급 전에 한 번 더 걸러내는 장치를 제공한다.

2017년 이후 공인 CA는 인증서 발급 전 CAA 레코드를 확인하는 절차를 사실상 필수로 수행한다. 따라서 CAA는 선언적 설정 한 줄로 끝나 보이지만, 실제로는 전 세계 CA의 발급 절차 안에 들어간 정책 제어점이다.

- **📢 섹션 요약 비유**: CAA는 우리 회사 도장은 지정된 인감 담당자만 찍을 수 있다고 출입구에 붙여 두는 승인 명부와 같다.

## Ⅱ. 아키텍처 및 핵심 원리

CAA 레코드는 도메인 존에 게시되며, CA는 인증서 발급 요청을 받으면 해당 도메인과 상위 도메인을 조회해 허용 정책을 확인한다. 대표 태그는 `issue`, `issuewild`, `iodef`이며, 각각 일반 인증서 허용 CA, 와일드카드 인증서 허용 CA, 위반 통지 수단을 뜻한다. 따라서 CAA는 암호 알고리즘이 아니라 <strong>발급 전에 수행되는 DNS 기반 정책 검사</strong>다.

| 태그 | 의미 | 활용 포인트 |
| :--- | :--- | :--- |
| `issue` | 일반 인증서 발급 허용 CA 지정 | 특정 공인 CA만 허용 |
| `issuewild` | 와일드카드 인증서 발급 허용 CA 지정 | `*.example.com` 통제 강화 |
| `iodef` | 정책 위반 보고 수단 | 메일·URL로 보안팀 알림 |
| flag | 향후 확장용 제어 비트 | 일반적으로 `0` 사용 |

아래 그림은 CAA가 인증서 발급 파이프라인 어디에 개입하는지 보여 준다.

```text
+----------------------------------------------------------------------+
|                  CAA check in certificate issuance                   |
+----------------------------------------------------------------------+
| Applicant --> CA request                                              |
|                |                                                     |
|                v                                                     |
|         CA queries DNS CAA record                                    |
|                |                                                     |
|       Allowed? -- Yes --> Validate domain --> Issue certificate        |
|                |                                                     |
|                +- No --> Reject / alert via iodef                     |
+----------------------------------------------------------------------+
```

예를 들어 `example.com. IN CAA 0 issue "digicert.com"`은 DigiCert 계열만 일반 인증서를 발급할 수 있다는 뜻이다. `issuewild`를 비워 두거나 특정 CA만 지정하면 와일드카드 인증서 발급 범위를 더 엄격히 제한할 수 있다. 또한 `iodef`를 설정해 두면 위반 시도나 정책 오류를 보안팀이 더 빨리 감지할 수 있다.

중요한 기술 포인트는 CAA가 상속처럼 동작할 수 있다는 점이다. 일반적으로 하위 호스트명에 명시된 CAA가 없으면 CA는 상위 도메인으로 올라가 정책을 찾는다. 따라서 서브도메인 위임 구조, 멀티 CA 사용 정책, 외부 DNS 호스팅 환경을 함께 고려해 설계해야 한다.

- **📢 섹션 요약 비유**: CAA는 도장 찍기 전에 결재선 명단을 먼저 확인하게 하는 규칙과 같아서, 명단에 없는 사람은 서류를 만들기 시작하기도 전에 멈추게 한다.

## Ⅲ. 비교 및 연결

CAA는 CT, DNSSEC, 온라인 인증서 상태 프로토콜 (OCSP, Online Certificate Status Protocol), 인증서 폐기 목록 (CRL, Certificate Revocation List)과 자주 함께 언급되지만 역할이 다르다. CAA는 발급 전 예방 통제이고, CT는 발급 후 공개 감시이며, DNSSEC는 DNS 응답 위변조 방지, OCSP는 발급된 인증서의 폐기 상태 확인에 가깝다. 즉 모두 인증서 생태계에 중요하지만 관여 시점이 다르다.

| 항목 | CAA | CT | DNSSEC | OCSP / CRL |
| :--- | :--- | :--- | :--- | :--- |
| 핵심 질문 | 누가 발급할 수 있는가 | 무엇이 발급되었는가 | DNS 응답이 위조되지 않았는가 | 지금도 유효한가 |
| 통제 시점 | 발급 전 | 발급 후 | 질의 시 | 운영 중 |
| 성격 | 예방 | 탐지·감사 | 무결성 보호 | 상태 검증 |
| 한계 | 허용 CA 범위만 제어 | 발급 자체를 막지는 못함 | CA 선택 정책은 아님 | 오발급 예방은 못 함 |

이 비교가 중요한 이유는 CAA 하나만으로 웹 PKI가 완성되지 않기 때문이다. 예를 들어 CAA가 있어도 DNS 응답이 변조되면 잘못된 정책을 볼 수 있으므로 DNSSEC가 도움이 된다. 반대로 CAA가 발급을 제한해도 이미 발급된 이상 인증서를 발견하려면 CT 모니터링이 필요하다.

실무적으로는 자동 인증서 발급 프로토콜 (ACME, Automated Certificate Management Environment)과도 연결된다. 자동 갱신 파이프라인이 여러 CA를 혼용하는 경우, CAA가 그 범위를 정확히 제한하지 않으면 운영 편의성 때문에 정책이 느슨해질 수 있다. 따라서 CAA는 "허용된 발급자 집합을 선언하는 거버넌스"로 보는 것이 맞다.

- **📢 섹션 요약 비유**: CAA는 사전 승인 명부, CT는 공개 게시판, DNSSEC는 게시판 위조 방지 봉인, OCSP는 이미 발급된 신분증이 취소되었는지 확인하는 전화와 같다.

## Ⅳ. 실무 적용 및 실무자 판단

대표적인 실무 시나리오는 기업이 운영 도메인과 외부 위탁 도메인을 함께 관리하는 경우다. 본사 도메인 `example.com`은 DigiCert만 쓰지만, 마케팅 서브도메인 `campaign.example.com`은 별도 서비스 사업자가 Let's Encrypt를 쓰는 식의 혼합 구성이 있을 수 있다. 이때 상위 도메인에만 단순 CAA를 걸면 하위 서비스 발급이 실패하거나, 반대로 하위 정책 누락으로 원치 않는 CA가 허용될 수 있다.

### 실무자 판단 체크리스트

1. 실제 사용하는 CA 목록과 CAA `issue` 정책이 일치하는가?
2. 와일드카드 인증서 사용 여부에 맞춰 `issuewild`를 별도로 관리하는가?
3. 서브도메인 위임 구조에서 상속 정책이 의도대로 작동하는가?
4. `iodef` 알림 채널이 유효하며 보안팀이 실제로 모니터링하는가?
5. DNSSEC, CT 모니터링, 인증서 자산 관리와 함께 운영되는가?

### 채택 / 회피 기준

- **채택**: 공개 HTTPS 서비스를 운영하고, 허용된 CA를 명확히 제한하고 싶은 대부분의 도메인
- **주의 필요**: 여러 위탁사가 각기 다른 CA를 쓰는 복잡한 서브도메인 구조, 자동화 파이프라인과 정책 불일치가 잦은 환경

### 안티패턴

- CAA를 설정해 두고 실제 인증서 발급 업체 변경 시 정책을 갱신하지 않는 경우
- `issuewild`를 고려하지 않아 일반 인증서 정책만으로 와일드카드까지 통제된다고 착각하는 경우
- CAA가 있으니 CT 모니터링이나 DNSSEC는 필요 없다고 보는 경우

- **📢 섹션 요약 비유**: CAA 운영은 문에 자물쇠를 다는 것에서 끝나지 않고, 누가 열쇠를 갖고 있는지 명단을 계속 최신 상태로 유지하는 일과 같다.

## Ⅴ. 기대효과 및 결론

CAA의 가장 큰 장점은 비용 대비 효과가 크다는 점이다. DNS 레코드 몇 줄만으로 허용되지 않은 CA의 발급 시도를 상당 부분 사전에 걸러낼 수 있고, 인증서 거버넌스를 문서가 아니라 실제 발급 절차에 연결할 수 있다. 특히 대형 조직처럼 도메인 수가 많고 위탁 운영이 섞인 환경에서 정책 일관성을 높이는 데 유용하다.

그러나 CAA는 만능 방패가 아니다. 이미 잘못 발급된 인증서를 회수해 주지도 않고, 허용된 CA 내부의 운영 실수까지 모두 없애 주지도 않는다. 또한 DNS 관리가 부정확하거나 응답 무결성이 약하면 정책 자체가 흔들릴 수 있으므로, CAA는 <strong>사전 제한 장치</strong>로 기억해야 한다.

결국 CAA의 핵심은 인증서 발급 권한을 도메인 소유자가 더 명시적으로 통제하게 만드는 데 있다. 웹 PKI가 "모든 신뢰된 CA가 잠재적으로 발급 가능"한 구조였다면, CAA는 그 범위를 줄여 "내가 허락한 CA만 발급 가능"한 구조로 좁혀 준다.

- **📢 섹션 요약 비유**: 좋은 CAA 정책은 누구나 출입 가능한 건물을 지정 출입자 명단이 있는 건물로 바꾸는 것과 같다.

### 📌 관련 개념 맵

| 개념 | 연결 포인트 |
| :--- | :--- |
| CA (Certificate Authority) | CAA 정책의 직접 통제 대상 |
| DNSSEC (Domain Name System Security Extensions) | CAA 조회 결과의 무결성을 강화 |
| CT (Certificate Transparency) | CAA가 막지 못한 오발급을 사후 감시 |
| ACME | 자동 발급 환경에서 CAA 정책 일치 여부가 중요 |
| `issuewild` | 와일드카드 인증서 허용 범위를 별도로 제어 |
| `iodef` | 정책 위반 또는 이상 시도 알림 채널 |

### 📈 관련 키워드 및 발전 흐름도

```text
다수 CA를 신뢰하는 웹 PKI
    |
    v
오발급 · 약한 고리 문제 부각
    |
    v
CAA (Certification Authority Authorization)
    |
    +- issue / issuewild 정책
    +- iodef 통지
    +- 발급 전 DNS 조회
    |
    v
DNSSEC · CT 모니터링 · 자동화된 인증서 거버넌스
```

이 흐름은 인증서 보안이 단순 신뢰 체인 검증에서, 발급 권한 통제와 공개 감시를 함께 갖춘 방향으로 발전하는 모습을 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. CAA는 "우리 집 열쇠는 이 열쇠집만 만들 수 있어요"라고 문 앞에 써 두는 규칙이에요.
2. 다른 열쇠집이 몰래 열쇠를 만들려 하면, 먼저 그 문구를 보고 안 된다고 멈춰요.
3. 그래서 우리 집 열쇠를 누가 만들 수 있는지 더 똑똑하게 지킬 수 있어요.
