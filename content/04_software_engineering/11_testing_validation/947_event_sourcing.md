## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 이벤트 소싱 (Event Sourcing) - CRUD 대신 상태 변경 이력(Event) 자체를 추가(Append-only) 저장은(는) 소프트웨어 공학의 핵심 개념으로, 복잡한 시스템을 체계적으로 설계·관리하기 위한 원칙과 기법이다.
> 2. **가치**: 이 개념을 올바르게 적용하면 소프트웨어의 품질·유지보수성·재사용성이 향상되고, 개발 생산성과 팀 협업 효율이 높아진다.
> 3. **판단 포인트**: 도입 시에는 비용·복잡도·조직 성숙도를 함께 고려해야 하며, 맹목적 적용보다 프로젝트 특성에 맞는 선택적 적용이 핵심이다.

---

## Ⅰ. 개요 및 필요성

CRUD는 마지막 상태만 남지만, 이벤트 소싱은 어떤 일이 일어났는지 순서대로 남긴다. 그래서 복원과 분석에 유리하다.

- **📢 섹션 요약 비유**: 결과만 적는 공책이 아니라, 풀이 과정을 모두 적는 공책이다.

## Ⅱ. 아키텍처 및 핵심 원리

상태는 이벤트를 순서대로 다시 적용해 만들어 낸다. 저장소는 append-only 로그처럼 동작한다.

```text
Event1 -> Event2 -> Event3 -> Replay -> Current State
```

| 요소 | 의미 |
|:---|:---|
| Event | 상태 변화 기록 |
| Replay | 이력 재생 |
| Snapshot | 재생 가속 |

- **📢 섹션 요약 비유**: 일기장을 다시 읽어 오늘의 기억을 떠올리는 것과 같다.

## Ⅲ. 비교 및 연결

이벤트 소싱은 CQRS와 잘 맞는다. 쓰기 모델은 이벤트를 기록하고, 읽기 모델은 이를 가공해 만든다.

| 구분 | Event Sourcing | CRUD |
|:---|:---|:---|
| 저장 대상 | 이벤트 | 현재 값 |
| 감사 추적 | 강함 | 약함 |
| 복원 | 재생 기반 | 백업 기반 |

- **📢 섹션 요약 비유**: 사진 한 장보다 연속 촬영 영상이 더 많은 이야기를 담는 것과 같다.

## Ⅳ. 실무 적용 및 실무자 판단

실무에서는 이벤트 버전 관리, 스냅샷 정책, 재생 성능을 함께 설계해야 한다.

점검 포인트는 다음과 같다.
1. 이벤트 스키마가 바뀌어도 복원이 가능한가?
2. 재생 시간이 너무 길지 않은가?
3. 감사와 분석 요구를 충족하는가?

- **📢 섹션 요약 비유**: 오래된 일기장도 읽을 수 있어야 한다.
