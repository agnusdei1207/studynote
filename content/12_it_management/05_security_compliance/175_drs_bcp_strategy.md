## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 업무 연속성 계획 (BCP, Business Continuity Plan)은 재난 상황에서도 핵심 업무를 이어 가기 위한 경영·운영 전략이고, 재해 복구 시스템 (DRS, Disaster Recovery System)은 그중 정보시스템 복구를 담당하는 기술 아키텍처다.
> 2. **가치**: BIA (Business Impact Analysis), RTO (Recovery Time Objective), RPO (Recovery Point Objective)를 기준으로 사람·프로세스·시스템 복구 우선순위를 정하면, 단순 백업을 넘어 실제 서비스 지속 가능성을 확보할 수 있다.
> 3. **판단 포인트**: 어떤 센터 유형을 고르느냐보다 정해 둔 목표 시간과 데이터 손실 범위를 실제 모의 훈련으로 달성할 수 있는지가 더 중요하며, failover뿐 아니라 failback까지 검증해야 한다.

---

## Ⅰ. 개요 및 필요성

DRS와 BCP는 "장애가 나면 백업에서 복원하면 된다"는 수준을 넘어선다. 자연재해, 대규모 정전, 랜섬웨어, 클라우드 리전 장애가 발생하면 문제는 단순히 서버가 꺼지는 데서 끝나지 않는다. 콜센터 스크립트, 대외 공지, 대체 인력, 협력사 연결, 재택 전환 절차까지 함께 흔들린다. 그래서 BCP는 업무 전체의 연속성을, DRS는 그중 IT 복구의 실행 경로를 맡는다.

이 구분이 필요한 이유는 백업만으로는 비즈니스가 바로 살아나지 않기 때문이다. 데이터 파일을 되살렸더라도 DNS (Domain Name System) 전환이 안 되어 있거나, 인증 체계가 막혀 있거나, 담당자가 누구인지 몰라 복구 선언이 지연되면 서비스는 여전히 멈춰 있다. 즉 "복원 가능성"과 "업무 지속 가능성"은 같은 말이 아니다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Disaster impact is broader than server failure                      │
├──────────────────────────────────────────────────────────────────────┤
│ Disaster / ransomware / region outage                              │
│   ├─ system downtime                                               │
│   ├─ workplace / network access disruption                         │
│   ├─ customer communication gap                                    │
│   └─ supplier / operator confusion                                 │
│                                                                    │
│ Backup only restores stored data                                   │
│ BCP + DRS restore business priority and recovery execution path    │
└──────────────────────────────────────────────────────────────────────┘
```

따라서 DRS/BCP의 필요성은 "자료를 살리는 것"이 아니라 **정해진 시간 안에 중요한 업무를 다시 돌릴 수 있는 상태를 만드는 것**에 있다. 기술, 운영, 의사결정 체계가 같이 준비되어 있어야 진짜 복구가 된다.

- **📢 섹션 요약 비유**: 비 오는 날 소풍이 취소되지 않게 하려면 우산만 준비해서는 안 된다. 실내 장소, 친구들 연락망, 도시락 옮길 사람, 선생님의 진행 순서까지 함께 준비해야 소풍이 계속된다.

## Ⅱ. 아키텍처 및 핵심 원리

DRS/BCP 아키텍처의 출발점은 BIA다. 어떤 업무가 몇 시간 멈추면 매출, 안전, 법규, 고객 신뢰에 어떤 손실이 나는지 파악하고, 그 결과로 MTPD (Maximum Tolerable Period of Disruption), RTO, RPO를 정한다. 그 다음에야 미러 사이트(Mirror Site), 핫 사이트(Hot Site), 웜 사이트(Warm Site), 콜드 사이트(Cold Site) 같은 복구 전략을 선택할 수 있다. 즉 센터 유형은 기술 취향이 아니라 **업무 영향 분석의 결과물**이다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ BCP-DRS architecture loop                                           │
├──────────────────────────────────────────────────────────────────────┤
│ BIA -> critical service tier -> MTPD / RTO / RPO                   │
│   │                                                                  │
│   ▼                                                                  │
│ Site strategy                                                        │
│   ├─ Mirror / Active-Active                                          │
│   ├─ Hot Site                                                        │
│   ├─ Warm Site                                                       │
│   └─ Cold Site                                                       │
│   │                                                                  │
│   ▼                                                                  │
│ Replication + runbook + communication tree                           │
│   │                                                                  │
│   ▼                                                                  │
│ Disaster declaration -> failover -> business operation -> failback   │
└──────────────────────────────────────────────────────────────────────┘
```

| 복구 전략 | 데이터 상태 | 대표 RTO/RPO 수준 | 비용 | 적합한 업무 |
| :--- | :--- | :--- | :--- | :--- |
| Mirror / Active-Active | 실시간 동기화, 즉시 전환 가능 | RTO 거의 0, RPO 거의 0 | 매우 높음 | 결제, 금융 거래, 24x7 핵심 서비스 |
| Hot Site | 시스템과 데이터 대부분 준비 | 수분~수시간 / 짧음 | 높음 | 핵심 대민 서비스, 주요 업무 시스템 |
| Warm Site | 장비와 일부 데이터 준비 | 수시간~수일 / 중간 | 중간 | 중요하지만 즉시성은 덜한 업무 |
| Cold Site | 공간·기본 인프라만 확보 | 수일 이상 / 김 | 낮음 | 비핵심 업무, 장기 복구 대상 |

핵심 원리는 세 가지다. 첫째, **우선순위화**: 모든 시스템을 같은 수준으로 지키려 하면 비용이 감당되지 않는다. 둘째, **절차화**: 복구는 사람 기억에 기대지 않고 선언 기준, 역할, 통신 체계를 문서화해야 한다. 셋째, **반복 검증**: 설계 문서가 아니라 실제 모의 훈련 결과가 목표 달성 여부를 말해 준다.

- **📢 섹션 요약 비유**: DRS/BCP 설계는 병원 응급실 분류와 같다. 모든 환자를 같은 속도로 처리할 수 없으니, 가장 위험한 환자를 먼저 살릴 기준과 동선을 미리 정해 두는 것이다.

## Ⅲ. 비교 및 연결

DRS와 함께 자주 언급되는 개념으로 백업(Backup), 고가용성(High Availability), BCP가 있다. 비슷해 보여도 질문이 다르다. 백업은 데이터를 되살리는 수단이고, 고가용성은 장애를 덜 일으키게 하는 구조이며, DRS는 큰 장애 이후 재기하는 절차이고, BCP는 그보다 넓게 조직 전체의 업무 연속성을 설계한다.

| 개념 | 핵심 질문 | 강점 | 한계 |
| :--- | :--- | :--- | :--- |
| Backup | "데이터를 되살릴 수 있는가?" | 데이터 보존의 기본 수단 | 업무 재개 절차와 인력 대응을 보장하지 않는다. |
| High Availability | "장애가 나도 끊기지 않게 할 수 있는가?" | 국소 장애를 자동 흡수 | 대규모 재난이나 리전 상실에는 부족할 수 있다. |
| DRS | "재난 후 얼마나 빨리 IT를 복구할 것인가?" | 시스템 복구 경로와 목표를 명확히 함 | 업무 우선순위와 조직 커뮤니케이션은 혼자 해결 못 한다. |
| BCP | "핵심 업무를 어떻게 계속할 것인가?" | 사람·프로세스·시설·IT를 통합 관리 | 기술 아키텍처가 약하면 실행력이 떨어진다. |

이 비교에서 실무적으로 특히 중요한 것은 **고가용성이 DRS를 대체하지 못한다**는 점이다. 이중화, 클러스터, 멀티 Availability Zone이 있어도 같은 리전이 모두 손상되거나 계정, DNS, 인증 체계가 함께 마비되면 별도의 DR 전략이 필요하다. 반대로 DR 센터만 있어도 인력 연락망과 의사결정 체계가 없으면 BCP가 성립하지 않는다.

클라우드 환경에서는 전통적 전산센터 용어가 바뀌었을 뿐 본질은 같다. 멀티 리전 복제, Infrastructure as Code, 불변 백업, 자동 failover는 현대적 구현 방식일 뿐, 여전히 BIA와 복구 목표가 선행되어야 한다.

- **📢 섹션 요약 비유**: 백업은 비상식량, 고가용성은 튼튼한 집, DRS는 대피소, BCP는 가족 전체의 대피 계획과 같다. 어느 하나만 있어도 조금은 버티지만, 모두가 맞물려야 위기를 넘어간다.

## Ⅳ. 실무 적용 및 실무자 판단

실무에서 좋은 DRS/BCP는 문서가 두꺼운 체계가 아니라 실제로 훈련 가능한 체계다. 특히 모의 훈련은 책상 위 검토(Tabletop Exercise), 기술 failover 시험, 전체 서비스 중단 가정 훈련으로 나누어 반복하는 것이 효과적이다. 이때 단순 전환 성공 여부뿐 아니라 선언 시간, 연락 체계, 데이터 정합성, 복귀 절차까지 함께 측정해야 한다.

| 업무 유형 | 권장 전략 | 실무자 판단 포인트 |
| :--- | :--- | :--- |
| 금융 거래·결제 | Mirror 또는 Hot Site, 다중 회선, 실시간 복제 | RTO/RPO를 극단적으로 짧게 잡되 비용과 규제 요구를 함께 검토한다. |
| 전자상거래·고객 채널 | Hot/Warm 혼합, CDN (Content Delivery Network), DNS 전환 자동화 | 주문·결제·회원 핵심 흐름을 우선 복구하고 비핵심 기능은 단계 복귀시킨다. |
| 내부 ERP (Enterprise Resource Planning), 그룹웨어 | Warm 또는 Cold + 우선순위 기반 복구 | 핵심 마감업무 시점과 인력 대체 시나리오를 BCP에 포함한다. |
| 랜섬웨어 대응 환경 | 격리된 불변 백업, 신원 체계 복구, 클린 룸 구축 | 단순 복제가 아니라 감염 없는 재기동 경로를 별도로 준비한다. |

### 실무 체크리스트

1. BIA 결과가 실제 서비스 등급과 예산 배분에 반영되어 있는가?
2. DNS, 인증, 배치, 외부 연계, 운영자 접근 경로까지 DR 범위에 포함했는가?
3. failover뿐 아니라 원복(failback) 절차와 소요 시간을 검증했는가?
4. 정기 모의 훈련 결과가 런북(runbook), 연락망, 자동화 스크립트 개선으로 이어지는가?
5. 랜섬웨어 시나리오를 고려해 백업 불변성, 계정 복구, 로그 보존을 분리했는가?

### 자주 발생하는 안티패턴

- 백업 파일만 있으면 DR이 된다고 생각하는 운영
- 같은 리전, 같은 계정, 같은 네트워크 안에 백업과 운영을 함께 두는 구성
- DR 전환만 시험하고 원복 절차는 한 번도 검증하지 않는 운영
- 애플리케이션 의존성, 외부 연계, 운영 권한 체계를 DR 범위에서 빼는 설계

학습 정리에서는 **"DRS/BCP는 복구 센터 구축 자체가 아니라, 업무 영향 분석에 근거해 목표 시간과 손실 허용 범위를 설정하고 이를 모의 훈련으로 검증하는 통합 연속성 전략"**이라고 설명해야 설계·운영·감리 관점이 함께 살아난다.

- **📢 섹션 요약 비유**: 소방 훈련은 소화기를 창고에 사 두는 일이 아니라, 누가 벨을 누르고 누가 아이들을 데리고 나가며 어디에 모일지 실제로 몸에 익히는 연습과 같다.

## Ⅴ. 기대효과 및 결론

DRS/BCP를 제대로 구축하면 장애 자체를 완전히 없앨 수는 없어도, 장애가 매출 손실과 신뢰 하락으로 번지는 시간을 줄일 수 있다. 복구 목표가 명확해지고, 책임자와 절차가 분명해지며, 모의 훈련을 통해 조직이 실제 위기 대응 근육을 갖게 된다. 결국 효과의 본질은 시스템만 살아나는 것이 아니라 **핵심 업무가 계획된 순서대로 다시 돌아오는 것**이다.

물론 높은 복구 목표는 높은 비용을 부른다. 모든 시스템을 실시간 이중화할 수는 없고, 과도한 목표는 예산 낭비나 운영 복잡성으로 돌아올 수 있다. 따라서 기억해야 할 핵심은 DRS/BCP를 "최신 장비의 목록"이 아니라 **업무 중요도에 맞춘 복구 수준과 훈련 체계의 설계 문제**로 보는 것이다.

- **📢 섹션 요약 비유**: 좋은 비상계획은 모든 물건을 두 벌씩 사는 일이 아니라, 꼭 필요한 것부터 어떤 순서로 꺼내 쓸지 정해 놓는 생존 가방과 같다.

### 📌 관련 개념 맵

| 개념 | 연결 포인트 |
| :--- | :--- |
| BIA (Business Impact Analysis) | 업무 중단 영향과 복구 우선순위를 정하는 출발점이다. |
| RTO (Recovery Time Objective) | 서비스가 멈춰 있어도 되는 최대 허용 시간을 정의한다. |
| RPO (Recovery Point Objective) | 허용 가능한 데이터 유실 시점을 정의한다. |
| MTPD (Maximum Tolerable Period of Disruption) | 비즈니스가 버틸 수 있는 절대 중단 한계를 설정한다. |
| High Availability | 평상시 장애 흡수 구조로 DR 전략과 상호 보완 관계다. |
| ISO 22301 | 업무 연속성 관리 체계(BCMS, Business Continuity Management System)의 대표 표준이다. |

### 📈 관련 키워드 및 발전 흐름도

```text
위험 식별
    │
    ▼
BIA (Business Impact Analysis)
    │
    ▼
MTPD / RTO / RPO 설정
    │
    ▼
Mirror · Hot · Warm · Cold 전략 선택
    │
    ▼
복제 · 런북 · 연락망 · 자동화
    │
    ▼
모의 훈련 / failover / failback 검증
    │
    ▼
지속 개선형 BCP / DRS 거버넌스
```

이 흐름은 재난 대응이 단순 백업에서 시작해, 영향 분석과 훈련 기반의 연속성 관리 체계로 발전하는 과정을 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. BCP는 비가 오거나 길이 막혀도 소풍을 계속할 수 있게 미리 다른 계획을 세워 두는 거예요.
2. DRS는 도시락이 망가졌을 때 바로 다른 도시락을 꺼내 먹을 수 있게 준비해 두는 장치예요.
3. 그리고 진짜 중요한 건 준비물만 쌓아 두는 게 아니라, 친구들과 선생님이 실제로 어떻게 움직일지 연습해 보는 거랍니다.
