## 핵심 인사이트 (3줄 요약)

> 1. **본질**: 앰배서더 (Ambassador) 패턴은 레거시 또는 다국어 클라이언트 옆에 프록시를 두어 원격 서비스 호출의 공통 기능을 대신 처리하는 클라우드 패턴이다.
> 2. **가치**: 클라이언트 코드 수정 없이 재시도, 인증, TLS, 관측성, 프로토콜 변환 같은 기능을 외부화할 수 있다.
> 3. **판단 포인트**: 직접 코드 수정이 어렵고 아웃바운드 호출 정책을 공통화해야 할 때 앰배서더의 효과가 가장 크다.

---

## Ⅰ. 개요 및 필요성

레거시 애플리케이션은 대개 원격 호출을 단순 HTTP 요청 수준으로 구현해 두었기 때문에, 클라우드 환경에서 요구되는 재시도, 타임아웃, 인증서 관리, 분산 추적을 코드에 다시 넣기가 어렵다. 특히 소스 수정이 어렵거나 여러 언어 클라이언트가 섞여 있으면 공통 기능이 중복된다.

```text
+----------------------------------------------------------------------+
|                 레거시 클라이언트의 직접 호출 문제                   |
+----------------------------------------------------------------------+
| Legacy App ----------------> Cloud Service                            |
|    |                                                                 |
|    +-- 재시도 없음                                                   |
|    +-- TLS / 인증 직접 처리 부담                                     |
|    +-- 장애 시 연쇄 실패 가능                                        |
|    +-- 로깅/추적 구현이 언어별로 흩어짐                              |
+----------------------------------------------------------------------+
```

앰배서더 패턴은 이 문제를 <strong>클라이언트 옆의 대리 프록시</strong>로 해결한다. 클라이언트는 로컬 주소만 호출하고, 실제 원격 서비스와의 복잡한 통신 책임은 앰배서더가 맡는다.

- **📢 섹션 요약 비유**: 외국어를 못하는 대표 대신 통역사와 수행비서가 해외 미팅을 챙겨 주는 구조가 앰배서더 패턴이다.

## Ⅱ. 아키텍처 및 핵심 원리

앰배서더는 보통 사이드카 컨테이너나 로컬 프록시 형태로 배치된다. 핵심은 <strong>클라이언트의 outbound 호출을 로컬 프록시로 우회시키고</strong>, 그 프록시가 정책 적용 후 원격 서비스로 전달하는 것이다. 이 구조 덕분에 애플리케이션 코드는 비즈니스 호출만 유지한다.

```text
+----------------------------------------------------------------------+
|                    Ambassador 패턴의 호출 흐름                       |
+----------------------------------------------------------------------+
| Client App --localhost---> Ambassador Proxy ---> Remote Service        |
|                         |                                             |
|                         +-- Retry / Timeout                           |
|                         +-- mTLS / Auth                               |
|                         +-- Protocol Transform                        |
|                         +-- Logging / Trace                           |
+----------------------------------------------------------------------+
```

| 기능 | Ambassador 역할 | 대표 구현 |
|:---|:---|:---|
| 재시도·타임아웃 | 일시 장애 시 정책 기반 재호출과 빠른 실패 처리 | Envoy retry, timeout |
| 인증·보안 | mTLS, 토큰 전달, 인증서 갱신 처리 | Envoy, cert-manager |
| 프로토콜 변환 | HTTP ↔ gRPC, 헤더 주입, 포맷 변환 | Envoy filter, custom proxy |
| 관측성 | 로그, 메트릭, Trace ID 전파 | OpenTelemetry, Jaeger |
| 속도 제한 | 호출 폭주 차단과 보호 | Rate limit filter |

앰배서더는 프록시이지만 모든 프록시와 같지 않다. 주 목적은 <strong>클라이언트 아웃바운드 호출의 공통 기능 외부화</strong>이며, 인바운드 트래픽 분산이나 전사 메시 제어와는 초점이 다르다.

- **📢 섹션 요약 비유**: 출장 담당 비서가 항공권, 통역, 통행증, 회의 일정, 통화 기록까지 대신 챙겨 주면 당사자는 회의 내용만 신경 쓰면 되는 것과 같다.

## Ⅲ. 비교 및 연결

앰배서더는 Sidecar, Reverse Proxy, Service Mesh와 자주 비교된다. 위치는 비슷해 보여도 해결하려는 범위가 다르다. 앰배서더는 개별 애플리케이션의 outbound 통신을 보조하는 데 초점을 맞춘다.

| 비교 대상 | 앰배서더 패턴과의 차이 | 적합 상황 |
|:---|:---|:---|
| Sidecar Pattern | 사이드카는 더 넓은 배치 방식이고, 앰배서더는 그중 아웃바운드 통신 특화 형태 | 레거시 호출 정책을 로컬에 붙일 때 |
| Reverse Proxy | 리버스 프록시는 주로 인바운드 요청을 서버 앞에서 처리 | 외부 요청 진입점 보호와 로드밸런싱 |
| Service Mesh | 서비스 메시는 프록시를 전 서비스에 일괄 적용하는 인프라 수준 | 조직 전체 트래픽 정책을 통합할 때 |
| Client SDK | SDK는 코드 안에 기능을 넣고, 앰배서더는 코드 밖으로 뺀다 | 코드 수정이 어렵거나 언어가 다양할 때 |

실무적으로 앰배서더는 서비스 메시의 개별·부분 적용판처럼 볼 수 있다. 즉 전사 메시를 깔기에는 부담스럽지만, 특정 레거시 애플리케이션의 외부 호출 품질을 끌어올려야 할 때 유용하다.

- **📢 섹션 요약 비유**: 개인 통역사는 특정 임원 한 명을 돕고, 회사 공용 통역 시스템은 전사 회의를 다 돕는다는 차이와 비슷하다.

## Ⅳ. 실무 적용 및 실무자 판단

앰배서더는 레거시 클라우드 전환, 외부 SaaS 호출 보호, 언어가 다른 서비스들의 공통 네트워크 정책 적용에 잘 맞는다. 특히 애플리케이션을 건드리지 않고 정책을 붙여야 한다는 조건이 있으면 선택 가치가 높다.

반대로 서비스 메시가 이미 조직 전체에 적용돼 있고 같은 기능을 제공한다면 별도 앰배서더는 중복 투자일 수 있다. 또한 단순한 클라이언트 하나에만 정책 몇 개가 필요하다면 SDK나 공통 라이브러리가 더 저렴할 수 있다.

### 판단 체크리스트

1. 클라이언트 코드를 수정하기 어렵거나 수정 위험이 큰가?
2. 재시도, 인증, 추적, 타임아웃 정책을 여러 클라이언트에 공통 적용해야 하는가?
3. outbound 호출 품질 문제가 실제 운영 장애로 나타났는가?
4. 서비스 메시나 공통 SDK와 비교했을 때 운영 복잡도가 감당 가능한가?

### 안티패턴 및 오답 포인트

- 단순 프록시를 모두 앰배서더라고 부르며 목적 차이를 설명하지 못하는 경우
- 인바운드 리버스 프록시 문제를 앰배서더로 해결하려는 설계
- 이미 서비스 메시가 있는 환경에서 동일 기능의 앰배서더를 중복 배치하는 설계

- **📢 섹션 요약 비유**: 통역사가 필요한 회의인지, 건물 안내 데스크가 필요한 상황인지, 회사 전체 번역 시스템이 필요한지 구분해야 비용 낭비가 없다.

## Ⅴ. 기대효과 및 결론

앰배서더 패턴을 적절히 쓰면 레거시 코드 무수정, 공통 정책 중앙화, 언어 독립성, 운영 가시성 향상이라는 효과를 얻는다. 특히 점진적 현대화 전략에서 큰 장점이 있다. 거대한 레거시를 한 번에 고치지 않고도 클라우드 요구사항을 외부에서 흡수할 수 있기 때문이다.

결론적으로 앰배서더는 프록시 하나 더 두는 것이 아니라 <strong>클라이언트 통신 책임을 비침습적으로 분리하는 전략</strong>이다. 따라서 코드 변경 비용이 높고 운영 정책 통일이 중요할수록 선택 가치가 커진다.

| 기대효과 | 구체적 내용 |
|:---|:---|
| 비침습적 현대화 | 레거시 코드 수정 없이 클라우드 정책 적용 |
| 공통 정책 중앙화 | 재시도, 인증, 추적을 프록시에서 일괄 관리 |
| 언어 독립성 | Java, C, Python 등 다양한 클라이언트에 동일 적용 |
| 운영 가시성 향상 | outbound 호출의 로그·메트릭·추적을 통합 확보 |

- **📢 섹션 요약 비유**: 오래된 TV에 스마트 셋톱박스를 붙여 본체를 바꾸지 않고도 최신 서비스를 쓰게 만드는 방식이 앰배서더 패턴과 비슷하다.

| Service Mesh | 앰배서더 개념이 전사 수준으로 확장된 구조 |

| OpenTelemetry | 관측성 기능을 앰배서더에 통합할 때 자주 연결됨 |

### 📈 관련 키워드 및 발전 흐름도

```text
레거시 클라이언트 직접 호출
    |
    v
정책 중복 · 인증 부담 · 장애 전파
    |
    v
Ambassador Pattern
    |
    +---> Retry / Timeout
    +---> Auth / mTLS
    +---> Trace / Logging
    +---> Protocol Transform
            |
            v
비침습적 현대화 · 공통 정책 중앙화 · 운영 가시성 향상
```

이 흐름은 앰배서더가 네트워크 호출 주변의 공통 관심사를 코드 밖으로 이동시키는 패턴임을 보여 준다.

### 👶 어린이를 위한 3줄 비유 설명

1. 외국 친구에게 말하기 어려운 아이 옆에 통역 친구를 붙여 주는 것과 같아요.
2. 아이는 자기 말만 하면 되고, 통역 친구가 번역하고 예의도 챙기고 기록도 남겨요.
3. 그래서 아이는 숙제를 바꾸지 않아도 더 똑똑하게 이야기할 수 있어요.
